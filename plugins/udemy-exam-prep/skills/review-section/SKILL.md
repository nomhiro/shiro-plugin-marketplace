# review-section

R3（[[create-section]] の最終承認）のあと、Udemy へのアップロード前に、**全問を人間の読み方で1問ずつ読む**工程です。
任意工程ですが、出題言語と出典の言語が違う講座（英語ドキュメントから日本語の問題を作る等）では実施を強く推奨します。

## 起動例

```
/udemy-exam-prep:review-section 3
/udemy-exam-prep:review-section all
全セクションの日本語を精読して直して
```

## なぜ機械スキャンだけで済ませないか

実績: ある講座で6本300問を、正規表現（訳語の禁止リスト）とカタカナ語の頻度集計で
スキャンしたが、**製品名の和訳と直訳調の日本語の大半を拾えなかった。** その後、
1セクション1サブエージェントで全問・全カラムを1問ずつ読ませたところ**約400件**見つかった。

- 製品名の和訳は語ごとに訳し方が違う（「ホストされる〜」「ホスト型〜」「〜者」「〜器」）ので、
  禁止リストは**見つけた後にしか**書けない
- 直訳調・意味の通らない文は、どの単語も正しいので語彙の検査では原理的に拾えない
- 出典が別製品のページ・正答が出典と食い違う、は文脈を読まないと分からない
  （[[exam-validator]] の検証5・`check_sources.py` の `source_scope` は候補を絞るだけ）

**機械スキャンは精読の後の回帰防止に使う**（手順6）。精読の代わりにはならない。

## 前提

- 対象セクションが [[create-section]] を完走し、R3 で承認済みであること
- `sections.md` / `question-bank.md` / 各セクションの `quiz.csv` があること

## 手順

### 手順0: 比較元を固定する（修正前に必ず）

不変条件の検査は「修正前」との比較なので、**修正前の状態を固定してから始める。**

- git 管理下なら、修正前の状態がコミット済みであることを確認する（`git status` がクリーン）。
  未コミットならユーザーにコミットするかを確認する（**コミットはユーザーの判断。勝手にしない**）
- コミットしない・git 管理外なら、修正前の `quiz.csv` を `.work/review/<slug>.orig.csv` に
  コピーしておき、手順5で `--base` に渡す

### 手順1: 精読（1セクションに1サブエージェント・並列）

**同じメッセージ内に複数の Agent tool 呼び出しを置いて並列起動する。** 1エージェントに
複数セクションを持たせない（後半のセクションほど読みが浅くなる）。

各エージェントへの指示テンプレート（`<...>` を埋めて渡す）。**`<scripts>` はオーケストレータが
プラグインの scripts フォルダの絶対パスに置き換えてから渡す**（サブエージェント側で
`CLAUDE_PLUGIN_ROOT` が解決できるとは限らない。実績: 修正エージェントには
プラグインキャッシュの絶対パスを書いて渡した）:

````
あなたは演習問題集の精読レビュアーです。<folder>/quiz.csv の全 <N> 問を、
全カラム（Question / Answer Option 1-6 / Explanation 1-6 / Overall Explanation）
について1問ずつ読み、日本語と内容の問題を指摘してください。修正はしません。

## 読み方
- 次のコマンドで10問ずつ出力し、全問を読む（抜き取りにしない・飛ばさない）
  python "<scripts>/check_invariants.py" <folder>/quiz.csv --show 1-10
  python "<scripts>/check_invariants.py" <folder>/quiz.csv --show 11-20
  ...
- 正規表現やキーワード検索で代用しない。問題文から Overall Explanation までを
  受講者が読む順に読む

## 指摘の分類
- A: 製品名・機能名・UI 名・ロール名・API/パラメータ名の和訳・カタカナ化
     （原語のまま書くべきものを訳している）
- B: 翻訳調・意味の通らない文・意味の誤り（原文の直訳で日本語として不自然、
     主語と述語が噛み合わない、訳し違えで事実が変わっている）
- C: 表記ゆれ（同じものを問題内・セクション内で違う書き方をしている）
- 出典と正答の食い違い・別製品の出典に気づいたら、種別を B とし要確認に「事実」と書く

## 出力（<out> に Markdown の表で書く。返信は件数の要約だけ）
| 問題# | カラム | 原文抜粋 | 種別 | 推奨修正 | 要確認 |
- 原文抜粋は CSV のセルから**そのままコピー**する（20-40字。言い換えない）
- 推奨修正は置き換え後の文字列。原語が分からなければ要確認に「原語」と書き、
  推奨修正は空でよい
- 最後に「A x件 / B y件 / C z件 / 要確認 w件」と、セクション内で見つけた
  表記ゆれの一覧（どの表記が何回）を書く

## 禁止
- quiz.csv を編集しない。サブエージェントを起動しない（fork も含む）
- 完了報告の前に <out> が書けていることを自分で読み直して確かめる
````

レポートは必ずファイルに書かせる（戻り値は途中で切れる）。出力先は `.work/review/<slug>-findings.md`。

### 手順2: サブエージェントの主張を抜き取りで機械照合する

**完了報告を成果物の根拠にしない。** レポートのファイルがあるか・件数が報告と合うかを見たうえで、
各レポートから数件ずつ抜き取り、`原文抜粋` がその問題のそのカラムに**実在するか**を確かめる。

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/check_invariants.py" <folder>/quiz.csv --show <問題#>
```

- 抜粋が実在しない（言い換え・捏造）指摘が混ざっていたら、そのレポートは全件を照合し直す
- 「全問読んだ」「日本語で書かれている」のような**自己申告は検証の代わりにしない。**
  言語・形式の主張はスクリプトで確かめる（実績: 「確認済み」と報告された内容が
  機械照合で食い違っていたことがある）

### 手順3: 統一表記シート（CONVENTIONS）を1枚作る

全セクションのレポートを集約し、**講座全体で1枚**の統一表記シートを `.work/review/CONVENTIONS.md` に作る。
セクションごとに作らない（本ごとに表記が割れ、講座内の表記ゆれを新たに作る）。

シートの構成（実績のある形）:

```markdown
# 修正時の統一表記ルール（全セクション共通・この表記に厳密に従う）

## 用語（製品・機能・UI・ロール名は原語のまま）
- <原語>（「<見つかった和訳1>」「<和訳2>」はすべてこれに直す）
- 例外: <一般語として日本語のままでよい用法>（例: 人間のレビュー担当の意味の「評価者」）
- <UI のペイン名・組み込みロール名は英語の正式名>

## 一般語の訳語（日本語のまま書くもの）
- <定訳>（例: transparency は「透明性」）/ <統一するカタカナ>（例: 「ベクトル」、「ベクター」は使わない）
- <Domain 名と一致させる表記>（例: スペースの有無を Domain 列と合わせる）

## 文体
- 各 Explanation の冒頭は <正誤印>（「正解。」は「正解です。」に直す等）

## 絶対に変えてはいけないもの（不変条件）
- Question Type / Correct Answers / Domain 列
- 空でない選択肢の数・並び順、正誤（正しい選択肢は正しいまま、誤答肢は誤りのまま）
- 各 Explanation N の冒頭の正誤印（N が Correct Answers に含まれれば正解の印）
- 出典 URL、バッククォート内のコード・パラメータ名
- 意味・事実関係。訳を直すだけで、問題の論点を変えない

## 要確認の扱い
（下記「要確認の扱い」をそのまま貼る）

## 書き込み方法
（下記手順4の書き込み方法をそのまま貼る）
```

- 用語の行は、レポートの A と C から**実際に見つかった訳し方を全部**列挙する（修正エージェントが同じ語を探せるように）
- 迷った用語は、この時点で要確認として解決してからシートに載せる（修正エージェントごとに判断させない）

### 要確認の扱い

- **問題が引用している出典 URL の英語版**を開いて原語を確認する。取得手段は
  [[research-cert-docs]] のベンダー別レシピ（`vendor` に応じた公式ドキュメント検索・fetch）に従う
- 原語が確認できなければ、**英語ラベルを創作しない。** 自然な日本語にする
  （もっともらしい英語の機能名を作ると、存在しない機能名を教えることになる）
- 事実に関わる指摘（出典と正答の食い違い・別製品の出典）は、**出典で裏付けが取れた場合だけ**直す。
  問題そのものの妥当性が崩れている場合は直さずにユーザーへ報告し、差し替えは
  [[create-section]] の手順（question-author への再起草依頼）に戻す

### 手順4: 修正（1セクションに1サブエージェント・並列）

各エージェントに渡すもの:

- そのセクションの `-findings.md`
- **統一表記シートの全文（全エージェントに同一のテキスト）。** 要約・抜粋して渡さない
  （エージェントごとに渡した文面が違うと、直した結果の表記が割れる）

書き込み方法（シートにも貼る）:

- `quiz.csv` は Python で読み（`read_rows`）、編集後は必ず `write_rows` で書く（BOM 無し）

  ```python
  import sys; sys.path.insert(0, r"<scripts>")   # scripts フォルダの絶対パスに置き換えて渡す
  from validate_quiz_csv import read_rows, write_rows
  ```

- 書いた後に `python "<scripts>/validate_quiz_csv.py" <quiz.csv>` を実行し、
  FAIL が無いこと・新たな長さ警告が出ていないこと（出たら改行で段落を分ける）を確認する
- **`quiz.csv` 以外（`quiz.raw.csv`・`sources.md`・`question-bank.md`）は触らない。** git commit しない
- 日本語と英単語の間のスペースのような**全体に一律で効く整形**は修正エージェントに任せず、
  オーケストレータが全セクションに対して一括で行う（エージェントごとに判断が割れる）

> **修正後に `quiz.raw.csv` から再シャッフルしない。** 精読の修正は `quiz.csv` にだけ入っている。
> `shuffle_options.py` は原本 `quiz.raw.csv` から混ぜ直すので、再シャッフルすると修正が
> 黙って消える。`shuffle_options.py` の raw ドリフト検知（`quiz.csv` の内容が `quiz.raw.csv` の
> シャッフルでは説明できなければ止まる）が警告したら、再シャッフルせずに止まる。
> どうしても混ぜ直す必要があるときは **`--adopt`**（`quiz.csv` を正として原本を作り直してから
> 混ぜ直す。精読の修正は残る）。**`--force` で押し切らない**（原本から混ぜ直し、精読の修正が消える）。
> 差分の確認だけなら `--check-drift`（何も書かない）。

### 手順5: 修正後の検査（すべてスクリプトで）

```bash
# 1. 不変条件: 修正前（git HEAD または手順0のコピー）と比べて、文章以外が動いていないか
#    git で固定した場合（比較元は HEAD。--ref で変えられる）
python "${CLAUDE_PLUGIN_ROOT}/scripts/check_invariants.py" <folder>/quiz.csv --sections sections.md
#    手順0でコピーした場合
python "${CLAUDE_PLUGIN_ROOT}/scripts/check_invariants.py" <folder>/quiz.csv --sections sections.md \
  --base .work/review/<slug>.orig.csv

# 2. CSV 形式
python "${CLAUDE_PLUGIN_ROOT}/scripts/validate_quiz_csv.py" <folder>/quiz.csv

# 3. ドメイン配分・本横断の重複
python "${CLAUDE_PLUGIN_ROOT}/scripts/validate_exam.py" --sections sections.md \
  --bank question-bank.md <folder>/quiz.csv

# 4. 文体・正誤印・glossary の禁止訳語、出典
python "${CLAUDE_PLUGIN_ROOT}/scripts/check_style.py" <folder>/quiz.csv --sections sections.md
python "${CLAUDE_PLUGIN_ROOT}/scripts/check_sources.py" <folder>/quiz.csv --sections sections.md
```

`check_invariants.py` が見るもの: 行数とヘッダー / `Question Type`・`Correct Answers`・`Domain` 列 /
空でない選択肢の番号 / 各行の出典 URL の集合 / 各 `Explanation N` の冒頭の正誤印が
`Correct Answers` と整合するか（印は `--correct-mark` / `--incorrect-mark`、無ければ front matter の
`style.explanation_markers`、それも無ければ「正解です。」「不正解です。」。英語の講座は印を指定する）。

**FAIL が出たら、その問題を修正前の版と突き合わせて戻す。** 文面修正で正解・出典が動くのは
すべて事故である（修正エージェントが「ついでに」選択肢を消す・出典を差し替えることがある）。

最後に、修正エージェントの主張も抜き取りで照合する。findings の `推奨修正` から数件選び、
修正後の該当セルに入っているか（`--show`）と、統一表記シートの「直す前の表記」が
全セクションから消えているか（`grep -c`）を見る。

### 手順6: 回帰防止（機械スキャンはここで使う）

精読で確定した「使ってはいけない訳語」を、`sections.md` front matter の `glossary`
（`check_style.py` が禁止訳語を FAIL にする）へ昇格させる。以後の作問・修正で同じ和訳が
戻ってきたら機械で止まる。

```yaml
glossary:                       # リスト。要素は term / forbid / allow_context
  - term: evaluator             # 原語で書く用語
    forbid: [評価器, 評価者]      # 使ってはいけない表記（部分一致）
    allow_context: [人間の評価者] # 任意。forbid を含むが正当な言い回し
```

**精読で見つかったものだけを載せる**（想像で禁止語を足さない。
一般語としての正当な用法まで落とすと、検査を無視する習慣ができる）。

### 手順7: 報告

```
section{N} の精読レビューが完了しました。

- 指摘: A x件 / B y件 / C z件（要確認 w件 → 出典で確認 u件・自然な日本語に v件）
- 修正: n件（統一表記シート: .work/review/CONVENTIONS.md）
- 直さずに報告する問題: （問題の妥当性に関わるもの。問題#と理由）
- 検査: check_invariants OK / validate_quiz_csv OK / validate_exam OK / check_style OK
- glossary に追加した禁止訳語: k件

差分を確認のうえ、コミットするかを指示してください。
```

## 引数

`$ARGUMENTS` にセクション番号（1つ）または `all`。`all` のときは手順1と手順4を全セクション並列で行い、
手順3の統一表記シートは全セクションのレポートがそろってから1枚だけ作る。

## してはいけないこと

- 機械スキャンの結果だけで「日本語は問題なし」と判断する
- 精読と修正を同じエージェントにやらせる（読みながら直すと、直した箇所の周辺しか読まなくなる）
- セクションごとに別々の統一表記シートを作る・シートを要約して渡す
- 原語が確認できない用語に英語ラベルを創作する
- 修正後に `quiz.raw.csv` から再シャッフルする（混ぜ直すなら `--adopt`。`--force` は修正を捨てる）
- 検査を通さずにアップロードへ進む・ユーザーの確認なしにコミットする
