# upload-practice-tests

ブラウザ操作（Claude in Chrome を第一手段、Playwright MCP を代替）で、既存の Udemy コースに演習テストをアップロード・設定・更新するオーケストレータスキル。

実装の詳細は [[udemy-bulk-upload]] に従います。このスキルはセクション横断のオーケストレーションに集中します。

## 起動例

```
/udemy-exam-prep:upload-practice-tests
Udemy のコースに問題集をアップロードして
コースXXXに各セクションの quiz.csv を反映して
```

## 前提条件

- **Claude in Chrome が第一手段**（ユーザーのログイン済み Chrome をそのまま使える）。使えなければ Playwright MCP（プラグイン同梱）。手段の選び方とツールの対応表は [[udemy-bulk-upload]]「ブラウザ手段」
- Playwright を使う場合のみ: Chrome ブラウザが閉じている。**Playwright のブラウザは普段の Chrome とプロファイルが別**なので、普段のブラウザで Udemy にログイン済みでもセッションは引き継がれない。Playwright のウィンドウでユーザー自身にログインしてもらう
- 各セクションフォルダに `quiz.csv` が作成済み（[[create-section]] 実行後）
- コースが作成済みかつ**有料設定済み**（無料コースは演習テスト追加不可）

## ユーザーから受け取る情報

**ユーザーに聞く前に、プロジェクトの `udemy-course-meta.md` を読む。** [[create-udemy-course]] と本スキルのステップ4a が、コース URL（コース ID）と「演習テスト quizId 対応表」（テスト名・quizId・セクションフォルダ・問題数）を記録している。そこに無いものだけをユーザーに聞く。

1. **コース管理ページの URL**（例: `https://www.udemy.com/instructor/course/XXXXX/manage/curriculum/`）— まず `udemy-course-meta.md` から
2. **各テストの quizId** — まず `udemy-course-meta.md` の対応表から。無ければカリキュラムページの `編集` リンクから読む
3. **アップロード対象** — 全セクション or 特定セクションのみ

### コースが公開済みかを確かめる

更新の手段はコースの状態で決まる。ログイン済みのページから API で読める:

```javascript
await (await fetch('/api-2.0/courses/<courseId>/?fields[course]=is_published,status_label',
  { credentials: 'include' })).json()
```

| 状態 | 既存テストの更新手段 |
|---|---|
| **公開済み（`is_published: true`）** | **編集画面ヘルパーで問題ごとに書き換える**（[[udemy-bulk-upload]]「多数の問題を書き換える」）。受講者の受験結果を失わないよう、**テストの削除→再作成はしない** |
| 下書き・未公開 | 書き換えを基本とし、テストの構成そのものを作り直すときだけ削除→再作成してよい |

> 実績: 公開中コースの6本300問を、テストを削除せず編集画面ヘルパーで書き換えた。quizId・設定・受講者の結果はそのまま残った。

テスト設定値は `sections.md` の front matter から自動で決まる（下表）。ユーザーが別値を指示した場合はそれに従う。

**本ごとの値はスクリプトから取る**（front matter を目で読んで写さない）。

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/profile.py" sections.md
```

出力の `slug` がセクションフォルダ名、`title` が Udemy に入れるテスト名、
`questions` が期待問題数、`minutes` が制限時間。**投入件数の検証にもこの
`questions` を使う**（`mode: mixed` では本ごとに違うため、全本同数を期待すると誤検出する）。

| 項目 | 値 |
|------|---|
| 時間（分） | `mode: mock-exam` は front matter の `exam.minutes` をそのまま（本番と同条件）。**`mode: mixed` は本ごとに違うので `profile.py` の出力の `minutes` を使う。** どちらも無い場合は `問題数 × 1.5` |
| 合格最低点（%） | 70 |
| 質問と回答の順序をランダム化 | **ON**（必須） |

## パイプライン

### ステップ1: CSV 事前検証

検証ロジックの唯一の定義元であるスクリプトを直接実行する。

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/validate_quiz_csv.py" section0*/quiz.csv
```

規約の詳細は [[quiz-csv-format]] を参照。

**あわせて解説の整合・文体も検査する**（形式検証では「正解番号が誤答肢を指している」
を検出できない）。front matter に `style` が無くても正誤印 x `Correct Answers` の整合は
既定の印（先頭が「正解」/「不正解」）で検査され、WARN が出る。`glossary` があれば禁止訳語を FAIL にする。

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/check_style.py" section0*/quiz.csv --sections sections.md
```

### ステップ1.5: ★ R4 レビュー断面（FAIL 検出時のみ） ★

事前検証で FAIL が1件でもあった場合、**ユーザーに修正方針を確認してから自動修正する**。FAIL ゼロなら本ステップはスキップ。

```
CSV 事前検証で N 件の問題を検出しました。修正方針を確認してください。

【検出された問題】
─────────────────────────────
[FAIL 1] section02-mock-exam-2/quiz.csv Row 17
  種類: multi-select with 1 correct answer
  問題テキスト冒頭: 「...」
  提案された修正: Question Type を 'multi-select' → 'multiple-choice' に変更
─────────────────────────────
[FAIL 2] section05-mock-exam-5/quiz.csv (header)
  種類: BOM detected at file head
  提案された修正: ファイルを utf-8（BOM無し）で書き直し
─────────────────────────────
[FAIL 3] section03-mock-exam-3/quiz.csv Row 8
  種類: has 15 columns, expected 17
  提案された修正: 空ペアを追加して17カラムに揃える
─────────────────────────────

選択肢:
- 「提案どおり修正して進めて」: 全ての提案修正を自動適用してアップロードへ
- 「FAIL Xだけ手動で確認したい」: 該当行を表示して個別判断
- 「中止」: アップロードを中止して、人間が手動で修正
- 「全部やり直し」: 該当セクションを /udemy-exam-prep:create-section で再生成
```

| ユーザー応答 | 動作 |
|------------|------|
| 「提案どおり修正」 | Python で全FAIL を自動修正 → 再検証 → 通れば次へ |
| 「FAIL Xを確認したい」 | 該当の問題文・選択肢・解説を全表示して個別判断 |
| 「中止」 | アップロードを中止して終了 |
| 「再生成」 | upload を中断し、`/udemy-exam-prep:create-section N` の実行を案内 |

**重要:** 自動修正が信頼できないケース（`multi-select` → `multiple-choice` の変換等）は、ユーザーが「提案どおり」と承認した場合のみ実行する。silently に行わない。

### ステップ2: ログインとコース管理ページ移動

[[udemy-bulk-upload]] の「ステップ2-3」を実行する。

**ログインが必要な状態に当たったら、そこで停止してユーザーに依頼する。** 資格情報を自分で入力してはいけない。

### ステップ3: 各セクションの処理ループ

`sections.md` の各セクションに対して以下を実行する。

1. 該当する演習テストがコースに既存か確認
   - 既存 → 「テストの問題入れ替え」フロー（ステップ4b）
   - 無し → 「新規テスト追加」フロー（ステップ4a）
2. 設定値を更新（時間・合格点・ランダム化ON）
3. `quiz.csv` をアップロード

### ステップ4a: 新規テスト追加フロー

[[udemy-bulk-upload]] の「ステップ4-6」を実行する。

1. カリキュラム編集で「カリキュラム項目を追加」→
   「演習テスト 認定資格準備の時間制限付き試験」→ タイトル入力 →
   **「演習テストを追加」**（ボタン名の実測は [[udemy-bulk-upload]] ステップ4）
2. タイトルはセクション名のみ（「セクションN:」プレフィックスは含めない）。
   **講座の表示言語に合わせる。** 日本語講座なら
   `<試験コード> 模擬試験 第N回（全N問）` の形で揃える。
   同じ出品者の既存講座があれば、その表記に合わせてカタログ内で統一する
3. **編集ページへ移動する:**
   `https://www.udemy.com/course/<courseId>/manage/practice-test/?quizId=<quizId>`
   （**`/instructor` を付けると 404**）。設定値を更新して保存
4. **投入用 CSV を作る。** 素の URL のまま投入すると出典がテキストで保存され、受講者はクリックできない。
   `python "${CLAUDE_PLUGIN_ROOT}/scripts/linkify_csv.py" section0*/quiz.csv --out-dir .upload` で
   出典行の URL を `<a href>` にした CSV を `.upload/<セクションフォルダ>/quiz.csv` に作り、`validate_quiz_csv.py` を通す
   （手順と実績は [[udemy-bulk-upload]]「出典 URL はリンクにして投入する」）
5. 「質問を追加」→「一括アップロード」。**一括アップロードはテストの既存問題をすべて置き換える**（追加ではない）
6. **ボタンは押さず** モーダル内の `input[type="file"]` に `.upload/<section-folder>/quiz.csv` を渡す
   （Claude in Chrome は find で ref を得て `file_upload`、Playwright は `setInputFiles`）
7. **「問題が作成されます。」**を待ち、「閉じる」（`exact: true`）を押す

**先に6本まとめて作成し、`quizId` を記録してから1本ずつ設定＋投入する**のが速い。
記録先は `udemy-course-meta.md` の「演習テスト quizId 対応表」（列: 演習テスト名 / quizId / セクションフォルダ / 問題数 / ドメイン配分）。次回の更新ではここから読むので、ユーザーに URL を聞き直さずに済む。

**注意:** 演習テスト専用コースは**最大6テストまで**。

> **上限ちょうどまで作るとカリキュラムページが「エラー」を表示する。**
> 「演習テスト専用コースでは、最大で6個の演習テストを含めることができます。」
> が赤いエラーとして出るが、これは**上限到達の案内で異常ではない**。
> 6本そろっていれば無視してよい（実績: これを異常と誤認しかけた）。

### ステップ4b: テストの問題入れ替えフロー

**全問を CSV 側の内容に差し替えるなら、CSV 一括アップロードで置き換える**（テストは消さないので quizId・設定は残る。1本数十秒）。
手順はステップ4a の4〜7と同じ。投入後にページを再読み込みし、編集画面ヘルパーの `auditBg(1, N)` で全問を quiz.csv と照合してから
（出典リンクの有無も見る）「変更内容を公開」を押す。**公開するまで受講者の版は変わらない。**

> 実績: 公開中の講座の6本300問を、この方法で差し替えた。全問の本文・正解が quiz.csv と一致し、出典320件がリンクになり、
> 件数・ドメイン配分は API で変わっていないことを確かめてから公開した。

**一部の問題だけを並びを変えずに直すなら、編集画面での書き換え**（問題の並びや設定が残る）。多数の問題は [[udemy-bulk-upload]]「多数の問題を書き換える」のヘルパーで、公開は「公開」に従う。**1本ずつ・1タブで進める**（並行実行は逆効果。実績は同スキル参照）。**テスト自体を削除→再作成するのは最終手段**（構成そのものを作り直すとき。受講者の受験結果が失われる可能性がある）。**公開済みのコースでは削除→再作成しない**（上記「コースが公開済みかを確かめる」）。手順は [[udemy-bulk-upload]]「既存テストの問題を入れ替える場合」を参照。

API DELETE 後もカリキュラムページにテスト枠が残ることがあるので **UI の「削除」ボタンで確実に削除**する。テスト削除はバックグラウンド処理なので、削除完了を待ってからステップ4a に移る。

### ステップ5: 結果報告

```
アップロード完了
  - section01-mock-exam-1: 60問 (120分, 合格70%, ランダム化ON)
  - section02-mock-exam-2: 60問 (120分, 合格70%, ランダム化ON)
  ...
  - 合計: N問 / Mテスト

未実施のリリース前作業:
  1. プロモーション動画（任意）
  2. 審査提出
  3. 公開
```

**公開方針はプロジェクトの `CLAUDE.md` を優先して読む。** プロジェクトによっては、ユーザーの承認のうえで審査提出・公開（「変更内容を公開」を含む）を自動化の対象に変えている（`CLAUDE.md` のワークフロー図や方針欄に、変更日とともに書かれている）。その記載があればそれに従って押してよい。**記載がなければ、審査提出と公開ボタンは押さない。** ここは人が判断する工程。

> 実績: あるプロジェクトでは `CLAUDE.md` でユーザー承認のうえ公開も自動化対象に変えていたのに、本スキルの「押さない」と食い違っていた。プロジェクトの方針を先に読む順序にした。

公開するときの手順（更新メッセージの書き方、ダイアログが開いてから入力すること、メール通知をオフにすること）は [[udemy-bulk-upload]]「公開」に従う。

### 更新履歴を残す

既存テストを更新・公開したら、`udemy-course-meta.md` の「更新履歴」に追記する（無ければ節を作る）。次に更新する人が、Udemy に載っている版と反映方法を追えるようにする。

```markdown
### 更新履歴

- **YYYY-MM-DD <更新の要旨>（対象: N本・M問）**
  - 修正内容: <何を直したか。詳細ファイルがあればその名前>
  - 反映方法: 編集画面で問題ごとに書き換え（テストは削除せず、quizId・設定は維持）
  - 検証: auditBg で全問の保存内容を CSV と照合し不一致0件。API で件数・ドメイン配分・問題タイプの内訳も確認
  - 公開: 各テストで「変更内容を公開」を実行
    - 更新メッセージ: 「<送った文面そのまま>」
    - 指導目的のお知らせ（メール通知）: オフ
```

**検証結果は実際に得た値を書く**（`auditStatus()` の `mismatch` / `err` の件数、API の `count`）。公開していなければ「公開: 未実施」と書く。

### 公開の一歩前まで整えて渡す

公開しない方針のときも、押さないことは「何もしない」ではない。**押すだけの状態にして、
足りないものがあれば名指しする**。リロードしてから実測する:

| 確認項目 | 読み方 |
|---|---|
| コースの状態 | ヘッダーに `下書き` / `公開中` / `審査中` |
| 公開ボタン | `button` の `disabled` を読む。**enabled なら Udemy 側の必須要件は充足** |
| タイトル / サブタイトル | 残り字数カウンタ |
| 言語・レベル・カテゴリ | `select` の `name` と選択中の `option` テキスト |
| コース画像 | `img` の `src` に `course/750x422/<courseId>_` が入っているか |
| 想定する学習者 | 値の入った textbox の件数（学習目的 + 必須条件 + 対象受講者） |
| 価格 | 通貨と価格帯の `select` |
| バリデーションエラー | **`必須` の文字列一致は説明文中の自著テキストを拾う。** 前後を見て本物か確かめる |

> 演習テスト専用コースには**動画の最低尺要件が無い**。
> `0分のビデオコンテンツがアップロードされました` と出ていても、
> 公開ボタンが enabled なら動画は必須ではない。

### ★ 検証は API を第一手にする（snapshot 解析より確実）

Udemy の内部 API はログイン済みのページから読める。**snapshot のテキスト解析より
桁違いに正確**で、ドメイン配分や形式比率まで一撃で数えられる。

```javascript
// 1本の投入結果を集計する
const r = await fetch('/api-2.0/quizzes/<quizId>/assessments/'
  + '?page_size=200&fields[assessment]=section,assessment_type',
  { credentials: 'include' });
const j = await r.json();
const byDomain = {}, byType = {};
(j.results || []).forEach(a => {
  byDomain[a.section] = (byDomain[a.section] || 0) + 1;
  byType[a.assessment_type] = (byType[a.assessment_type] || 0) + 1;
});
({ total: j.count, byDomain, byType });
```

- `count` が期待問題数と一致するか
- `section`（= CSV の `Domain` 列）の内訳が `sections.md` のノルマと一致するか
- `assessment_type` の内訳が `question_types` の比率と一致するか

1問の中身も API で読める。**選択肢別解説と全体解説の両方が入ることを確認する**
（`prompt.feedbacks` と `prompt.explanation` の両方が埋まる。
編集画面の「各回答選択肢の説明 / 質問全体に対する1つの説明」のラジオは
手動作成用の設定で、一括アップロードには影響しない）。

```javascript
await fetch('/api-2.0/quizzes/<quizId>/assessments/?page_size=1'
  + '&fields[assessment]=prompt,correct_response,section', { credentials: 'include' });
```

> **テストの設定値（時間・合格点・ランダム化）は API では読めない。**
> `/api-2.0/quizzes/<id>/?fields[quiz]=...` は 404 を返す。
> **編集画面のフォーム値を読む**のが確実（講師が見る値そのもの）。

### ★ 演習テストは「末尾」ではなく「現在位置の下」に追加される

6本を続けて追加すると**1本目が最後に来る**。

> 実績: ①②③模試1模試2模試3 の順に作ったのに、
> 並びが ②③模試1模試2模試3① になった。

並べ替えのドラッグは jQuery 系で不確実なので、
**タイトルを位置に合わせて付け替える**ほうが確実で検証もしやすい。
どの quizId にどの CSV を入れるかは自分で決められるので、
「位置 → 入れる CSV → 付けるタイトル」の対応表を先に作ってから進める。

### 投入結果は3段で検証する（件数だけでは足りない）

API が使えない場合、または UI 上の見え方を確かめる場合はこちら。
アップロードの「成功アラート」だけを根拠にしない。**リロードしてから**次の3つを見る。

**① 件数と欠番** — 問題一覧は `tab "N. 問題文…"` として描画される。

> **リロード直後は0件に見える。** 「値が空」と「まだ描画されていない」は
> 区別できない。**期待件数に達するまで待ってから判定する**こと。
>
> 実績: reload 直後に `tab` が 9 件（= 問題0件。固定タブだけ）しか取れた。
> 10秒待って数え直すと 72 件（= 63問 + 固定タブ9）に揃った。ここで
> 「投入に失敗した」と判断すると、成功しているテストを削除して作り直す
> 事故になる。**固定タブの分だけ下駄が乗る**ので、期待値は
> 「問題数 + 固定タブ数」で持つか、`tab "N. ` の数だけを数える。

```bash
grep -oE 'tab "[0-9]+\. ' snap.md | grep -oE '[0-9]+' | sort -n | uniq | python -c "
import sys
ns=[int(l) for l in sys.stdin]
missing=[i for i in range(1,max(ns)+1) if i not in set(ns)] if ns else []
print(f'{len(ns)} 問 (1-{max(ns) if ns else 0}) 欠番={missing or None}')"
```

**② 設定値** — `spinbutton "時間（分）"` / `spinbutton "合格最低点（%）"` の値と
`checkbox "質問と回答の順序をランダム化" [checked]` を snapshot から読む。

**③ 1問を開いて中身を読む（これを飛ばさない）** — 件数と設定が揃っていても
**問題の中身が壊れていることがある。** 任意の1問を開き、次の4点を実際に読む。

- 選択肢が全件あり、**文が途中で欠けていないか**
- 正解の選択肢に `正解` バッジと `[checked]` が付いているか
- 選択肢ごとの解説と全体解説（出典 URL 込み）が入っているか
- 出典 URL が**リンク（`<a href>`）として保存されているか**（API の `prompt.explanation` に `<a` があるか。
  素の `https://...` だけなら未リンク。API が返すのは公開済みの版なので、公開前は編集画面の `auditBg` の `unlinked` で見る。
  未リンクなら `linkify_csv.py` の CSV で投入し直すか、ヘルパーの `'link'` モードでリンク化する）
- ドメインが全件登録され、正解のドメインが選択されているか

> 実績: 6本 360 問すべてで①②が正常だったが、**③で1問の選択肢が
> `Wrap the request in , , and tags` に壊れているのを見つけた。**
> CSV に書いた `<role>` `<context>` `<output>` が Udemy のサニタイザに
> 削除されていた。①②だけでは絶対に見つからない欠陥だった
> （現在は `validate_quiz_csv.py` のタグ検査が投入前に落とす）。

**問題文を CSV と機械照合するなら、スナップショットの YAML が
アポストロフィを `''` に二重化することに注意する。** 素で比較すると
`A regional airline''s ...` と `A regional airline's ...` が不一致になり、
実際には正常なのに欠陥として報告してしまう（実績: 1件の誤検知）。

## 保存の確認（飛ばすと壊れる）

**保存直後の画面表示とサイドバーの「完了済み」を成功の根拠にしてはいけない。**
Udemy は入力を**エラーも出さずに破棄する**ことがある。必ず**リロードして実際の値を読む**。

実測: お祝いのメッセージが 0 字で保存されたのに、保存時は「成功アラート」が出て
サイドバーも「完了済み」になっていた。コースメッセージの「完了済み」は歓迎・お祝いの
**どちらか片方でも立つ**ため、片方の欠落に気づけない。

### ドット付き文字列はリンク判定で落とされる

**この落とし穴の説明は [[create-udemy-course]] に置いている。**
実際に該当する欄（学習目的・必須条件・対象受講者・コース説明・コースメッセージ）を
入力するのはコース作成側のスキルなので、読む順序が逆にならないようにした。
テストのタイトルや問題本文を入力するときも同じ規則が効くので、
そちらを先に読むこと。

## ブラウザ操作の固有注意

[[udemy-bulk-upload]] の「エラーハンドリング」を参照。以下は主に Playwright で踏んだもの（Claude in Chrome でも UI 側の罠は同じ）。特に頻出:

- 「質問と回答の順序をランダム化」→ input の `id` を読んで `label[for="<id>"]` を押す。**親 generic は当たらないページがある**（実測: 1本目は成功、2本目で `intercepts pointer events`）
- ファイル投入 → ボタンを押さず `input[type="file"]` に `setInputFiles`
- テスト削除直後の新規追加でカウントエラー → 数秒待ってリトライ
- **アクセシビリティ名は保存後の再描画で落ちる。** `getByLabel('時間（分）')` や
  `getByRole('checkbox', {name: ...})` が突然解決しなくなるので、構造で取る:
  `input[type="number"]` の nth(0)=時間 / nth(1)=合格点、`input[type="checkbox"]` の first()=ランダム化
- **「質問を追加」の ＋ はアクセシビリティ名を持つ。** snapshot に
  `img "質問を追加"` として出るので **ref クリックで足りる**ことが多い
  （SVG の `use href` を DOM 走査する必要はなかった）。
  **ref が解決しない・`getByRole('button', {name: '質問を追加'})` が
  当たらないページがある**ので、そのときは `img` を内包する `button` を取る:

  ```javascript
  page.locator('button', { has: page.locator('[aria-label="質問を追加"]') }).first()
  ```

  実測ではこちらが6本すべてで安定した
- **カリキュラムの「追加」ドロップダウンは押した数だけ DOM に残る。**
  `button:has-text("認定資格準備の時間制限付き試験")` は N 個に当たって
  曖昧マッチで失敗するので、**毎回 snapshot を取り直して可視要素の ref を使う**
  （role 検索は可視要素だけに当たる）
- **問題一覧は `tab "N. 問題文…"` として描画される**（`generic` ではない）。
  投入件数の検証は `tab "N. ` を数える
- **成功モーダルが保存ボタンを覆う。** 一括アップロード後は「閉じる」を押してから
  設定を保存する。順序を逆にすると保存ボタンのクリックがタイムアウトする
  （**設定を先に保存してから投入する順序にすれば、この罠を避けられる。**
  実測で設定値は「質問を追加」へ進んでも保持された）
- **「閉じる」は `exact: true`。** 付けないと `img "モーダルダイアログを閉じる"` にも
  部分一致して strict mode violation になる
- **カリキュラム行の `編集` は link、`削除` は button で隣接している。**
  ref を取り違えると削除確認ダイアログが出る（`キャンセル` で無傷で戻れる）
- **`browser_run_code_unsafe` は `async () => { ... }` の形で渡す。**
  トップレベルの文は `SyntaxError` になる
- **1問だけ直したいときテストを削除しない。** 問題エディタで
  「質問を保存」すれば足りる（[[udemy-bulk-upload]]「既存テストの問題を入れ替える場合」）
- **ファイル選択ダイアログは滞留する。** `page.waitForEvent('filechooser')` を
  コード内で使うと未処理のダイアログが積み上がり、他のツールが
  `does not handle the modal state` で全滅する。**ボタンを押さず
  `input[type="file"]` に `setInputFiles` で直接渡す**のが安全
  （画像なら `accept` に `jpg` を含む input を選ぶ）
- 画面遷移で `beforeunload` ダイアログが出たら `browser_handle_dialog` で処理する

## 注意事項

- CSV のエンコーディング/BOM 起因のエラーが頻発するため、必ず事前検証ステップを飛ばさない
- **Udemy が配布するテンプレートの版を毎回確認する。** 一括アップロードのダイアログに
  ダウンロードリンクがある（2026-09 時点は `PracticeTestBulkQuestionUploadTemplate_V2.2.csv`）。
  取得してヘッダーを `scripts/validate_quiz_csv.py` の `HEADER` と照合する。
  実測では V2.2 のヘッダー17列は v2 と完全一致だった
- ユーザーの操作と並行しないこと（ブラウザの状態が壊れる）
- 全テスト更新の途中で失敗した場合、どのセクションまで完了したかを明示してリカバリ可能にする
