# 制作の自己改善の仕組み

講座を何十本も作ると、同じ失敗を何度も踏む。踏んだ失敗を**検出器（スクリプト）か、必ず通す関門か、
依頼文の決まり**のどれかに変えて、次の1本で踏まないようにする。このファイルはその仕組みを決める。

実際に起きたこと：教訓が「メモリ」「撮影担当への依頼文」「講座のスキル」「このプラグイン」の4か所に
別々に書かれ、古い記述（ぼかしで隠す、CLI で作って URL で直接飛ぶ）が残ったまま新しい規則と食い違った。
規則に反する道具（OS から窓を操作するスクリプト）も残った。効いたのは「報告 → 依頼文に1行足す →
次の担当がそれを読む」という短い循環で、弱かったのは (a) 教訓の置き場所が決まっていない、
(b) 講座固有の事実と一般の教訓が混ざる、(c) 古い記述を消す工程が無い、の3つだった。

## 1. 失敗 → 検出器 → 関門 → 書き戻し先

1行1件。**関門の列が「必ず回す検査」になる**（make-lecture-movie / make-practice-movie の該当節はここを正本にする）。

### 実践

| 繰り返した失敗（実測） | 検出器 | 関門 | 書き戻し先 |
|---|---|---|---|
| 個人情報・他プロジェクトの名前・ID・金額の映り込み | `ocr_mask.py` → `leak_check_ocr.py` | 組み立ての前。塗り残し 0 件。最後にコンタクトシートで全数を目視 | 講座の規則ファイル（git 管理外） |
| 寸法の違う枚が混ざる・描画が左上だけになる | `ingest_shot.py`（想定の寸法以外は記録しない） | 撮るたび | `record-practice-screen` |
| 強調枠が文字にかぶる・指す値を外す | `box_fit.py --check`／`cue_stills.py --sheets` | 組み立ての前。NG 0、全数を目視 | `record-practice-screen` |
| TTS の異常（ループ・途中の長い無音・別の文） | `qa_check.py`・`verify_tts.py` | `--audio-only` の直後。NG 0 | `tts-readings.md` |
| 画面に着くまでの手前が無い・CLI ばかりで管理画面が出ない | 撮影計画のレビュー | 撮る前に、区間の一覧に「検索 → 候補 → 一覧 → 作成」があるか | `record-practice-screen` |
| 課金の断定（「存在するあいだ課金」「無料」） | 台本のレビュー（`transcript-reviewer`） | 台本の確定前 | `make-practice-movie` の指摘の表 |
| リソースの残存 | 一覧の 0 件の画面と、CLI の出力のログ | 撮影の最後。残っていれば報告の先頭に「重大：残存リソース」 | `record-practice-screen` |
| デスクトップ・他の窓への副作用 | 依頼文の決まり（検出器は無い） | 依頼文に必ず入れる | `record-practice-screen` の最初の節 |
| 座学と実践で主張が食い違う | 撮影担当が同じトピックの座学の確定版の台本を読む | 台本の確定前 | 依頼文のテンプレート |
| OCR が1字の残り・上端で切れた行・小さい字・アバターを読めず 0 件で通る（4回） | コンタクトシートの全数目視と、上端・下端・塗った所の拡大 | 組み立ての前 | `record-practice-screen` |
| UI の状態を塗りで隠す（preview の札など） | `transcript-reviewer` の観点 | 台本の確定前 | `record-practice-screen` |
| 機能紹介に画面が無い（図だけ） | 初学者役・slide-reviewer の観点 | 台本の段階で「どの枚にどの画面」 | `quality-standards.md` 29 |

## 2. 教訓ファイル（講座側に1つ）

講座リポジトリに **1つだけ** 置く（例 `<講座>/.claude/course-lessons.md`。雛形は `templates/course-lessons.md`）。
座学と実践で分けない。メモリ・依頼文・スキルに散らさず、ここを正本にする。

- 1件の書式：
  `- [日付][レクチャー][種別] 教訓（1〜2行）。根拠：報告・コミット・フレーム。汎用度：講座固有｜クラウド一般｜Udemy 一般。状態：新規｜プラグイン反映済み（版）｜廃止（理由と置き換え先）`
- 種別は固定する：撮影／塗り／操作のくせ／後片付け／事実（一次資料）／台本／図解／読み／STT／リビール／小テスト／TTS／Udemy／権限／運用。
- **直さないと決めた裁定も書く**（却下した案と理由）。同じ指摘を何度も検討し直さないため。
- **「事実（一次資料）」は講座固有として扱い、プラグインへは上げない。**
- 撮影担当・作り直し担当への依頼文は、テンプレート（`templates/reshoot_prompt.md`）にこのファイルを
  **差し込んで**作る。依頼文の本体は講座ごとに書き直さない。

## 3. 担当の報告に「教訓」欄を必須にする

- 依頼文の報告の型に「新しく分かったこと（0〜3件、上の書式で）」を入れる。**0件でも「なし」と書かせる。**
- 親（取りまとめ役）は報告を受けたら教訓欄を教訓ファイルへ転記する。依頼文の本体は書き換えない
  （差し込みで次の担当に届く）。

### 制作者の新しい指摘は、その場でレビューの観点にする

制作者（ユーザー）から新しい指摘を受けたら、**その場で**次を行う。指摘は同じ形で再発する（例: 「形で解ける」問いは言い方を変えて10回以上）。

1. 教訓ファイルに1行足す（指摘の原文の引用と日付）
2. **レビューの観点に1項目足す**（slide-reviewer の追加観点ファイル・transcript-reviewer に渡す講座の方針・依頼文のどれか）。
   次の回から、制作者が見る前にレビュー担当が拾う
3. **置き場所は1か所に決める。** 同じ指示をメモリ・CLAUDE.md・規約・観点の3か所に書くと、片方だけ直って食い違う。
   正本を1つ決め、ほかの場所は正本を指す1行にする

## 4. レトロ（5本ごと、または区切りごと）

1. 教訓ファイルの「新規」を読み、重複をまとめる。
2. **昇格の判断**：同じ教訓が2本以上で出たか、1本でも重大（映り込み・残存リソース・デスクトップへの副作用）なら、
   「Udemy 一般／クラウド一般」としてプラグインへの反映候補にする。判断の基準は「別の分野の講座でも同じことが起きるか」。
3. **検出器にできるものは検出器にする。** 作ったら、**承認済みの全本にさかのぼって回す**
   （実測：空白の検出器を作ってさかのぼったら、承認済みの3本に空白が見つかった）。
4. **矛盾の掃除**：新しい教訓と食い違う記述を、メモリ・講座のスキル・依頼文・このプラグイン・スクリプトから探す。
   見つけたものは「廃止」と書き、置き換え先を示す。規則に反する道具は消すか、実行すると止まるようにする。
5. 反映したものに「プラグイン反映済み（版）」を付ける。プラグインの版を上げるときは、README の変更履歴に
   「どの現象の実測から来たか」を件数と現象で書く（講座名・レクチャー番号は書かない）。
6. 数値の根拠は「実測」か「見積もり」かを区別して書く（見積もりで「96.5% が 20 秒以内」としたものが、実測では外れていた）。
7. **検出器を作ったら、わざと厳しい閾値で1回回し、出力が出ることを確かめる。** 講座から講座へ写した検査が、
   条件の書き誤りで一度も働いていなかった。**教訓の1行で防げなかった失敗は、道具にする**（誤報が2回続いた報告 → 状態を数える道具）。
8. **道具を講座から講座へ写したら、写した向きを記録し、直したら写し元とプラグインにも返す。** 直しが片方の講座にしか入らず、
   写し元に不具合が残った。プラグインへの PR は区切りで状態（マージ済みか）を確かめる（PR が8日間マージされずに残った）。
9. 直したあとは、**検査とレビューをもう一度回してから**音声・レンダリングに進む（直した画面に新しい重なりが出やすい）。

## 5. 自律で進めるときの型

- 最初の数本は制作者の承認で基準を固め、そのあとで「機械の関門をすべて通ったら自動で承認」に切り替える。
- **止まって制作者に知らせる条件**を依頼文に書く：一次資料の食い違いで主張が決められない／想定外の課金が要る
  （高い SKU など）／外部（公開先）へ反映する前に許可が要る／承認済みの絵が変わる／パイプラインが壊れた／
  サインインが切れた（パスワードや多要素認証は入力しない）／作ったリソースが消せない。
- **段階ゲートで並列に回す。** 1本を「台本 → 親が初学者役のレビュー → 音声・スライド → 親がスライドのレビュー → 修正」
  の段階に分け、担当は段階ごとに止まって報告する。台本のレビューを音声より前に置くと、録り直しが減る
  （依頼文は `templates/script-review_prompt.md`）。担当には、親の文脈を丸ごと継ぐ分岐より、短い手順書を渡すほうが軽い。
- **分岐（フォーク）したサブエージェントは、さらにサブエージェントを起動できない。** レビュー役は親が回す前提で段階を切る。
- **並列の上限を決めておく。** 動画の制作は同時に 2 レクチャーまで（利用上限に当たって止まった）。
  ブラウザを使う担当は 4〜5 体が限度（各自がブラウザを立てると実機が飽和する）。
- **同じ1本を2人に渡さない。** 渡す前に、その回の音声フォルダが空か（＝誰も着手していないか）を親が確かめる。
  2人が同じ回の音声とスライドを上書きし合い、音声と画面の時刻が食い違った。担当を替えるときは、旧担当に
  着手済みかを**先に**聞く。
- **音声を作り始めたら台本は凍結する。** 台本の修正担当に凍結を知らせ、完了報告を受けてから音声を作らせる。
  他の回と言い方をそろえるときは、音声のある回に合わせて、音声前の回を直す。
- **完了の通知やサブエージェントの報告が来たら、その場で次の手順まで進める。** 「通知を待つ」と書いて手番を終えると、
  そのまま止まる（レンダリングの完了から約3時間止まった）。長い処理を投げる前に、終わった後の手順を決めておく。
- **プロセスは PID を指定して止める。** 名前で一括に止めると、並列の担当や MCP サーバーまで止まる。
  応答待ちのまま数時間残るプロセス（STT の呼び出しなど）は、中身（コマンドライン）を確かめてから止める。
  合成が書き終えた後に子プロセスだけ残ることもある。出力とメタ情報の時刻がそろっていれば、その結果は採用してよい。
- **外部ツールの版を固定する。** 版を付けずに呼ぶと最新版を取りにいき、公開直後の不具合（tarball が 404）で
  全部の処理が落ちた。版を上げるときは1本で通してから固定値を替える。
- **状態の一覧表を生成して、作業のたびに更新する**（制作・確認・公開先の状態）。制作者が書く列は再生成で引き継ぐ。
- 区切り（1レクチャーの完成）ごとに引き継ぎの文書を書き直す。区切りの報告は、作ったもの・公開先の状態・反映した改善（1行ずつ）。
  改善が無いときも「改善提案なし」と書く
- 自分で予約した起動（ウェイクアップ）が、作業が済んだ後に届くことがある。状態を確かめて「済」と返す
- 長い処理・Windows・ブラウザの運用は `windows-and-ops.md`
- 担当が途中で落ちたら（利用上限など）、痕跡（作業フォルダ・退避した音声・新しい mp4・変更ファイルの一覧）と
  残っているリソースを確かめ、リソースがあれば先に消してから、続きか最初からかを決める。
