# make-practice-movie

画面録画（`<basename>_rec.mp4`、複数パートは `_rec1.mp4, _rec2.mp4`…）と、レクチャー解説
ドキュメント・既存スライドを入力に、**録画パート専用の台本**（`<basename>_transcript_rec.md`）
を組み立てて、AI音声付きの実践レクチャー動画 `<basename>.mp4` を生成する。

> **位置づけ**：[[make-lecture-movie]] の姉妹スキル＝ハンズオン専用。座学は従来どおり
> `make-lecture-movie` が担当し、そちらは実践レクチャーを既定でスキップする。

## パイプライン

```
モードA  録画を置く → analyze → 【確認①】タイムライン確定 → _transcript_rec.md
         → transcript-check → 【確認②】台本レビュー → build
         → qa_check.py / leakcheck.py → transcript-reviewer → 差し替え

モードB  フレームを撮る → 塗り・強調 → 【検収①】強調を目視（cue_stills.py --sheets）
         → _transcript_rec.md → transcript-check → 【確認②】台本レビュー
         → 音声を先に合成 → build_rec.py --audio-dir → build --video-only
         → qa_check.py / leakcheck.py → transcript-reviewer → 差し替え
```

確認ポイントは2箇所（**タイムライン**と**台本**）。どちらも承認を得てから次へ進む。
モードBでは①が**強調の目視検収**に替わる（タイムラインは自分で決めているため）。

## モードBの作業ディレクトリの型（実証済み・作り直し8本）

区間の定義（画像・強調・塗り・ナレーション）を**1か所に置き**、そこから全部を生成する。
直すのはこのファイルだけにすると、「台本は直したが枠が古い」のような食い違いが起きない。

```
<basename>_rec.work/
  raw/                 撮ったままのスクリーンショット（上書きしない）
  make_recipe.py       R = [(src, ラベル, 強調の意図の範囲, 塗り, ナレーション), ...]  ← 正本
                       実行すると recipe.json（src/out/highlight/blackout）を書く
  make_json.py         R からナレーション frames.json、既存スライドの台本から slides.json を作る
                       （スライドの台本を直すときは (旧文, 新文) の置換リストで当てる）
  box_manual.json      box_fit が誤認する区間だけ手置きの枠（任意）
  recipe.json / frames/ / slides.json / frames.json   生成物
  old/                 作り直す前の版（比較用）
```

手順（`<SC>` はプラグインの `scripts/`。重い処理は優先度を下げて1本ずつ走らせる）:

```bash
python make_recipe.py                                  # recipe.json
python make_json.py .                                  # slides.json / frames.json
python <SC>/box_fit.py --work .                        # 強調枠を文字から 3px 以上離して置き直す（NG 0 を確認）
python <SC>/render_frames.py --work .                  # raw/ → frames/
python <SC>/cue_stills.py --frame-dir frames --out-dir stills --sheets   # 【検収①】全数を目視
python <SC>/build_rec.py frames.json --frame-dir frames --out-dir .. --base <B> --slides slides.json
                                                       # 見積もりパス：台本の骨組み _transcript_rec.md
python <SC>/practice_movie.py build <ID> --audio-only  # 音声だけ先に合成
python <SC>/qa_check.py ../<B>_transcript_rec.md       # 🔴 ここで TTS の異常を拾う（下記）
python <SC>/verify_tts.py ../<B>_transcript_rec.md --endpoint <Speech のエンドポイント>   # 🔴 音声を文字に戻して台本と照合
python <SC>/build_rec.py frames.json --frame-dir frames --out-dir .. --base <B> --slides slides.json        --audio-dir ../<B>_audio_rec --tail-sec 2.0      # 実尺で組み直す
python <SC>/practice_movie.py analyze <ID> --force
python <SC>/practice_movie.py build <ID> --video-only --force --slide-tail-seconds 1.0
python <SC>/qa_check.py ../<B>_transcript_rec.md ; python <SC>/leakcheck.py ../<B>.mp4
```

- 🔴 **TTS の異常は `--audio-only` の直後に拾う。** 合成音声はまれに、同じ文を繰り返す・
  途中に何十秒もの無音が挟まる（実測：1本の中で 148 秒）・途中で切れる。`build_rec.py --audio-dir` は
  **その wav の尺をそのままフレームの尺にする**ので、組んでからでは動画が間延びする。
  `qa_check.py` が「ループ疑い」「途中に長い無音」を出したら、**その wav を別の場所へ退避して
  `--audio-only` をもう一度**（無い wav だけ合成される）。退避は削除でなく移動にする（比較用）。
- 🔴 **合成音声が台本と無関係な文を読むことがある。** 実測（1本の中で4区間）：区間まるごと別の文
  （「教育的な講座は…」）、冒頭に余計な前置き（「ようこそ。オンライン講座へ…」）、冒頭の1文の脱落。
  **長さが近いと `qa_check.py` の比では見逃す。** `verify_tts.py` で STT に戻して台本と照合する
  （類似度・長さの比・冒頭の一致）。NG は退避して再合成し、もう一度照合する。
  - 原因の見当：生成型の TTS（Gemini-TTS）は、**スタイル指示（vertexai-tts-instruction.md）の内容に
    引きずられて文を作る**ことがある。事故の文面は「オンライン講座」「教育的な」など指示の語を含んでいた。
    別レクチャーの文が混ざった例もあったが、一時ファイルはプロセスごとに別なので、取り違えではなく生成とみられる。
  - 実測の頻度：作り直した約25本のうち、照合で見つかった本物の事故は1本あたり0〜4区間。
    **全区間の照合を、動画を組む前の必須工程にする。**
- 強調枠は **`box_fit.py` を通すまで信用しない。** 目分量の枠は文字に接する・かぶる
  （実測：10本で56件）。2px まで細くしても空きが取れない区間は、撮り直し時に行間を広げる
  （`record-practice-screen` の B-1）。
- **尺の上限で区間を削らない。** 作り直しでは README の手順をすべてたどると 20分を超えることがある
  （実測 16〜26分）。手順を飛ばすと受講者が再現できなくなるので、長さは受け入れ、制作者に尺を伝える。
- 撮影（ブラウザは1つしか使えない）と、別のレクチャーの組み立て・レビューは並行できる。
  組み立ては重いので**同時に2本まで**にする（メモリ不足でバックグラウンドの処理が落ちた実測あり）。

**`_rec.mp4` の入手経路は2つある。**

- **モードA**：制作者の画面録画を置く。試行錯誤やエラーがそのまま教材になる回に向く。
- **モードB**：[[record-practice-screen]] が、Claude 自身の画面操作を静止画で撮って組み立てる。
  手順と画面の対応を見せる回に向く。待ち時間が入らず、1枚だけ撮り直せる。

`_rec.mp4` が置かれた後の流れは共通だが、**モードごとに使う工程が違う**。

| 工程 | モードA（実録画） | モードB（静止画から組む） |
|---|---|---|
| `detect_events.py` で境界を拾う | **使う** | **使わない**（境界は自分で決めている） |
| `shift_lead.py` でナレーションを先行させる | **使う** | **使わない** |
| `--rec-lead-seconds` | **0 にする** | 既定のままでよい（区間頭＝画面の切替） |
| 沈黙率の調整手段 | 台本の加筆／区間の割り直し | **末尾余白（`--tail-sec`）** |
| 尺の決まり方 | 録画の実時間が先にある | **合成音声の実尺から決める**（下記） |

以下、**「モードA専用」と書いた節は、モードBでは読み飛ばしてよい**。

## ナレーションの重点：コードは「書き方」より「読み解き」

実践レクチャーの受講者は、**教材リポジトリを取得した状態**から始める（写経はしない）。
台本の重点は、**用意済みのコードが何をしていて、なぜそう書くのか**に置く。

- **環境準備は画面に残す。ただし語りは薄く。** 仮想環境の作成・依存の導入・設定ファイルの
  記入は受講者が必ずやる手順なので省かない。一方で尺の主役はコード解説なので、定型作業は
  短い一文で流し、待ち時間は無音のままにする。
- **設定値をレッスン間で流用させるときは、変数名の違いを必ず指摘する。** 入れる値は同じでも
  キー名が違う、という取り違えが起きる。
- **録画前にフォルダをクリーンに戻す**（仮想環境・キャッシュ・設定ファイルを消す）。
  前回の残骸があると準備の画面が撮れない。
- **エディタでコードを映している区間が本体。** ブロック単位で「**役割 → なぜこう書くか →
  試験でどう問われるか**」を語る。
- **「コメントに書いてあります」で済ませない。** 画面にコメントが出ていても、その場で意味を言い直す。
- **実行結果の区間は「どのフィールドを見るか」を言う。** 「成功しました」で終わらせない。
- **エラーや試行錯誤が録画に入っていたら、それは価値ある教材。** 何を疑い、どこを直したかを語る。

## 🔴 モードBの尺は「合成した音声の実尺」から決める

モードBではフレームの秒数を自分で決められる。ここで **`文字数 / cps × 1.15 + 余白`
の見積もりをそのまま完成尺に使わない。** 見積もりの余裕が、そのまま無音になる。

**2パスで組む。**

```
1パス目  台本 → TTS（音声だけ先に合成する）
2パス目  各 wav の実尺を測る → 尺 = 実尺 + 末尾余白 → フレームを組む → 動画化
```

- `build_rec.py --audio-dir <音声ディレクトリ>`（または `--durations <json>`）で実尺を渡す。
  **渡さないと見積もりに落ちる。**
- **末尾余白は 2.0 秒**が実測の最適値。7本の結果は
  **沈黙率およそ10%・最大の無音 3.7〜4.1秒・本ごとのばらつき 0.1秒**。
- 台本を直したら、**その区間の音声を再合成してから尺を測り直す**。
  テキストが変わらない区間の音声はキャッシュされるので、部分的な直しは安い。
- 見積もりパス（`--cps` / `--headroom` / `--pad-sec`）は、
  **音声をまだ作れない下見のときだけ**使う。

## 区間の粒度（音声と画面のズレを防ぐ）

**1区間＝ナレーション1〜2文＝1つの一貫した画面状態**が原則。1区間に複数の画面遷移を
まとめると、各文の発話タイミングと画面が一致せず「音声のほうが先に進む」ズレになる。
音声は区間の頭から流れるだけで、内部の遷移点に個別同期する仕組みはない。
**同期精度は区間の細かさに直接依存する。**

- 1区間は5〜30秒になることが多い。3文以上必要になったら境界を追加できないか検討する。
- 2〜3秒の断片は無理に独立させず、前後に統合してよい（無音として自然に吸収される）。
- （モードA）**初回 analyze（既定60枚）だけで区切りを決めない。** 等間隔サンプリングより細かい遷移は
  見えない。長い区間は `--max-frames` を増やして再analyzeし、遷移点を洗い出す。
- **偶発的な操作のブレはナレーションに反映せず、無音で流す。** セッション切れ・再認証・
  UI操作の迷いは、台本で言及しようとせず画面だけ動かす。文字数バジェットを使い切る必要はない。

### 境界は「画面が変化した瞬間」に機械的に合わせる（**モードA専用**）

> モードBでは、区間の境界＝自分が用意したフレームの切れ目なので、この節は不要。

等間隔フレームだけで境界を決めると、実際の操作より**1〜3秒後ろにずれる**。
「音声が少し遅れている」と言われる主因はこれで、一律シフトでは直らない。
`detect_events.py` で変化点を秒単位で列挙し、その時刻を境界にする。

- イベントは**種類も判別できる**。アプリ切替は変化量が大きく、スクロールや選択は小さい。
  切替の瞬間に境界を置くと体感精度が上がる。
- ミニマップやタブ行を検出範囲から外さないと誤検出だらけになる。
- `build` の `--rec-lead-seconds` は **0** にする（既定値はズレの上乗せになる）。

### さらに「ナレーションを先行させる」（**モードA専用**）

境界を実操作にぴったり合わせると、ナレーションと画面変化が**同時**になる。これは
視聴時に「遅れている」と感じられる。視聴者はまず画面変化に気づき、そのあと音声を
聞き始めるからである。`shift_lead.py` で各区間の開始を少し前倒しする
（**前倒し量は直前区間の余白で上限を切る**ので、詰まりすぎない）。

## 沈黙率を測って調整する

境界を実操作に合わせると、区間の実尺に対してナレーションが短くなり沈黙が増える。
一方で喋りっぱなしにすると視聴者の目が追いつかない。**録画パート全体で10〜20%**が目安。
`qa_check.py` が自動で測る。

- **埋める内容は中身のあるものにする。** 間を埋めるだけの言い換えは逆効果。
- **全部埋めない。** 依存の導入の進行、画面の読み込み、長い出力のスクロールは、
  受講者が画面を目で追う時間なので残す。
- モードBでは、フレームの秒数がナレーション長から決まるため、
  **末尾余白（`--tail-sec`）で沈黙率を制御する**。
  **実尺 + 2.0 秒**が実測の最適値で、7本を通して次の値に収まった。

  | 指標 | 実測 |
  |---|---|
  | 録画パートの沈黙率 | **およそ 10%**（目安帯 10〜20% の下端） |
  | 1区間の最大無音 | **3.7〜4.1 秒** |
  | 本ごとのばらつき | **0.1 秒** |

  見積もり（`--pad-sec` 2.5〜3.5秒）で組むと沈黙率が2割を超える。
  **余白を広げる前に、実尺を使っているかを疑う。**

## 映り込みを機械的に点検して消す

公開前に必ず点検する。**輝度の変化では見つからない。**

- `leakcheck.py`（**探索**）… 何が映ったか分からないときに、彩度の高い区間を洗い出す。
  開発画面はほぼ無彩色なので、写真サムネイルや色付きオーバーレイが際立つ。
  ヒットは必ず目視する。タイトルスライドや色付きの図は正当なヒット。
- `find_text_leak.py`（**照合**）… 消したい文字列が1枚分かっているとき、
  そのテンプレートを全編に照合して出現時刻を列挙する。
- **カット**：該当区間を台本の区間から外すだけでよい。短くなった分はフリーズ延長で吸収される。
- **塗りつぶし**：カットできない場所は、モードAなら正規化済み動画に前処理をかけ
  （元を退避してから）、モードBなら `redact.py` でフレームを直接潰す。**ぼかしは使わない。**

## 台本レビューでは「画面の値」と「台本の主張」を突き合わせる

タイムコードが合っていても、**言っている内容が画面と矛盾**していることがある。
`transcript-check` では検出できない。`agents/transcript-reviewer` に渡す。

- 各区間について、**画面に映っている実際の値**と台本の主張が一致するかを1件ずつ確認する。
- 数字の読み方も確認する。共有のプールと個別の上限を取り違えると意味が逆になる。
- **制作者のミスを演出にしない。** 「落とし穴が待っています」のような伏線や
  「実務でもよくやるミス」といった一般化は入れない。エラーは原因と対処だけを説明する。
- レビューの指摘は**そのまま鵜呑みにしない**。特に事実誤りの指摘は、自分でも一次情報に当たる。
  台本が直近で直っていて、指摘が既に解消済みのこともある。

レビューで繰り返し出た指摘（作り直し8本で、ほぼ毎回どれかが出た）:

| 型 | 例 | 直し方 |
|---|---|---|
| **たとえが仕様と逆** | 「管理者は部屋の鍵を持っていない」→ 実際は管理者はキーを取り出せる | たとえを入れたら、**画面の後半の手順と矛盾しないか**を読み返す。条件（「トークンで呼ぶ場合は」）を付ける |
| **条件の抜けた断定** | 「Owner では推論できない」（正しくは Entra ID 認証では） | スライド・台本・解説の3か所を同じ条件でそろえる |
| **デモが通った理由の取り違え** | 上位スコープから継承したロールで通ったのに、いま付けたロールの効果に見える | 「この環境では〜が効いているのですぐ通った。無い環境では待ち／エラーになる」と一言足す |
| **一次資料に無いエラー文言** | 記憶のエラーメッセージを台本に書く | 一次資料の文言か、実機で出た文言だけを書く。無ければステータスコードで言う |
| **強調が台本の指す値を外す** | 「200 が返りました」の 200 が枠の外 | 枠の意図の範囲を広げて box_fit をやり直す |
| **実測を公式のように言う** | 講座で試した挙動を一般の仕様として断定 | 「講座の検証では〜でした」と出典を言い分ける |
| **読点で終わる区間** | 「…を作り、」で区間が切れる | 区間ごとに別々に合成されるので、各区間を述語で言い切る |
| **「確実に」の過剰な約束** | 「instructions で強く指示すれば確実に使う」→ 保証されない（強制は `tool_choice`） | 保証の仕組みがあるものだけ「確実」と言う。モデルの振る舞いは「〜ことがある」 |
| **毎回そうなるように言う** | 「ここでは並列に呼ばれます」→ 受講者の手元では1件ずつのことがある | 画面の結果は「今回は」と言い、ぶれる可能性と、そのとき失敗ではないことを添える |
| **モデルが作った値をツールの結果と混同** | ツールは合計だけ返したのに、内訳の数字もツールの結果として読む | どの値をどこが出したかを言い分ける |
| **スライドの台本に旧版の記述が残る** | 旧スライドの台本を数か所だけ置換し、残りの文（料金・前提の数・エラーの例）が新しい手順と矛盾する | 置換リストで済ませず、スライドの台本は**全文を読み直して**新しい手順・事実と突き合わせる |
| **撮影後に README を直して画面と食い違う** | レビューで README を直したが、撮影済みのプレビューは旧文言 | 撮影の**前に** README の説明文を自己点検する（断定の条件・事実の裏取り）。食い違いが残ったら撮り直し候補として記録する |
| **フォルダー名の管理番号を読む** | 「L2-4 multistep tools のフォルダー」 | フォルダー名は番号を除いて読む（qa_check が拾う） |

## 前提条件（初回のみ）

1. **Python依存**：`pip install -r scripts/requirements.txt`
2. **音声合成の認証**：クラウドTTSを使う構成では、その認証を通しておく
3. **ffmpeg / ffprobe** が PATH にあること
4. **LibreOffice（soffice）** が PATH もしくは既定インストール先にあること

## サブコマンド

```bash
# 実効文字/秒（net cps）を既存成果物から再実測する
python scripts/practice_movie.py calibrate

# 録画の正規化・連結・フレーム抽出。区切り検討用の時刻対応表を出力
python scripts/practice_movie.py analyze <ID>

# タイムコード整合・文字数バジェット超過チェック（TTS前）
python scripts/practice_movie.py transcript-check <ID>

# TTS→スライドPNG化→セグメント合成→動画書き出し
python scripts/practice_movie.py build <ID>
```

| オプション | 対象 | 既定 | 説明 |
|---|---|---|---|
| `--max-frames <n>` | analyze | 60 | 抽出フレーム数の上限 |
| `--frame-scale <WxH>` | analyze | 1280x720 | 抽出フレームの解像度 |
| `--cps <n>` | check/build | 5.3 | バジェット計算に使う実効文字/秒 |
| `--fill-ratio <n>` | check/build | 0.9 | バジェットに掛ける充填率 |
| `--orig-volume <n>` | build | 0.18 | 録画の元音声を残す音量 |
| `--tolerance <n>` | build | 0.15 | タイムコード超過の許容比率 |
| `--rec-lead-seconds <n>` | build | 0.3 | 区間開始→ナレーション開始の無音。**モードAで実操作に境界を合わせたら 0** |
| `--audio-only` / `--video-only` | build | off | 音声だけ／動画だけ。**モードBは音声だけを先に作る** |
| `--force` | analyze/build | off | キャッシュを使わず再生成 |

`build_rec.py`（モードBのフレーム組み立て）側：

| オプション | 既定 | 説明 |
|---|---|---|
| `--audio-dir <dir>` | なし | **合成済み音声の実尺**で各区間の尺を決める（推奨） |
| `--durations <json>` | なし | 区間キー → 秒数の対応を直接渡す（音声が別の場所にあるとき） |
| `--tail-sec <n>` | 2.0 | 実尺に足す末尾の無音。**実測の最適値は 2.0** |
| `--cps` / `--headroom` / `--pad-sec` | 5.7 / 1.15 / 1.0 | **音声がまだ無いときの見積もり用**。実尺を渡したときは使われない |

## 台本フォーマット `_transcript_rec.md`

既存の `_transcript.md`（スライドパートの流用元）は**上書きせず温存**する。

```markdown
## スライド1: タイトル
（導入スライドのナレーション）

## 録画1 [00:12-01:48]: 仮想環境の作成と依存の導入
（この区間の実尺の文字数バジェット内で新規に書く。画面の動きと対応させる）

## スライド6: まとめ
（まとめスライドのナレーション）
```

- スライド行：`^##\s*スライド\s*(\d+)\s*[:：]`
- 録画行：`^##\s*録画\s*(\d+)\s*\[MM:SS-MM:SS\]\s*[:：]`（時刻は連結後の録画基準）
- 見出しに書かれた順＝再生順。

## 読み上げ表記（TTS の誤読対策）

TTS は英字の略語や記号を意図と違う読みにすることがある（例：`az` を「アズ」と読む）。
台本を書く前に **`../../references/tts-readings.md`（読み上げ表記一覧）** を見て、載っている表記は台本での書き方に直す
（例：`az login` → 「エーゼットログイン」）。適用は台本の**本文だけ**で、見出し行・スライド・画面の表記は元のまま。
誤読を見つけたら、直したうえでその一覧に追記する（他の台本にも同じ表記がないか洗い出す手順も一覧にある）。

## 長さフィットと「間」

- **文字数バジェット**：`floor(cps × fill_ratio × 区間長)`。
- ナレーションが**短い**場合：末尾に無音が残るだけで自然。無理に埋めない。
- **長い**場合：まず `--tolerance` までフリーズフレームで延長し、収まらなければ台本を短縮して
  該当区間だけ再合成する。
- スライドパートは座学と同じ「間」を使う。

## 出力レイアウト

```
lectures/<section>/
  <basename>_録画手順.md          # 事前：録画の指示書（モードA）
  <basename>_撮影計画.md          # 事前：撮影計画（モードB）
  <basename>_rec.mp4              # 入力：録画（git管理外）
  <basename>_rec.work/            # 作業用（git管理外）
    frames/                       #   モードB：組み立て用フレーム
    stills/                       #   モードB：強調の検収用（コンタクトシート）
  <basename>_transcript.md        # 既存：スライドパートの流用元（温存）
  <basename>_transcript_rec.md    # 本スキルが生成する台本
  <basename>_audio_rec/           # 出力：音声＋manifest（git管理外）
  <basename>.mp4                  # 出力：完成動画（git管理外）
```

**git に入れるのは、解説ドキュメントと `_transcript_rec.md` だけ。**
動画・音声・作業ディレクトリは管理外にする。作業ディレクトリに大きな中間生成物が
落ちているので、**`git add -A` を使わず、パスを明示してコミットする**。

## 収録で分かったことを資料へ書き戻す

実機で撮ると、**机上のレビューでは残っていた誤りが必ず出る**（実測7本で7本とも）。

- CLI のオプション名・値が違う、設定の組み合わせが保存できない、画面のラベルが違う、
  「ここで確認できる」と書いた場所に実際には出ていない、など。
- **その場で解説ドキュメントを直し、最終確認日を更新する。**
  あとでまとめて直すと、何が実測で何が記憶か分からなくなる。
- **できなかったことは「できない」と書き、回避策を2〜3通り添える。**
  受講者が最も必要とするのはここである。

## よくある落とし穴

- **長い区間＝音声と画面のズレ。** ビルドも `transcript-check` も通るのに、完成動画で
  ズレる。バジェットではなく**粒度**の問題なので、文字数を削っても直らない。
  区間を割り直す。
- **可変fps録画／無音声の録画**：正規化で吸収されるので問題にならない。
- **タイムコードだけ変更した再実行**：台本テキストが変わらない限り音声はキャッシュされる。
  区切りの調整はコスト0で試せる。
- **soffice は直列実行のみ。** 他のスライド変換と同時に走らせない。
- **`_rec.mp4` を上書きすると元録画が復元できない**構成が多い。置き換える前に退避する。
- **モードBで沈黙が多い。** 余白を詰める前に、**実尺を使っているか**を確かめる
  （文字数見積もりのままだと、余白をいくら詰めても2割前後から下がらない）。
- **強調の位置ずれは、動画を作ってからでは直しにくい。** 組み立て前に
  `cue_stills.py --sheets` で目視する。直すと音声の合成からやり直しになる。
- **TTS が途中で止まることがある。** 長い回（20区間前後）で接続が残ったまま停滞した実測あり。
  **manifest は完了分を再利用する**ので、プロセスを落として `--audio-only` から
  やり直せば、続きから進む。
