# record-practice-screen

実践（ハンズオン）レクチャーの**素材づくり**を担当するスキル。出力は
`lectures/<section>/<basename>_rec.mp4` で、そこから先は [[make-practice-movie]] が引き取る。

制作者が画面録画ソフトで撮る従来のやり方（モードA）に対して、本スキルは
**Claude がブラウザを操作し、状態ごとにスクリーンショットを撮って動画に組む**（モードB）。

## モードBを選ぶ理由

| | モードA（制作者のPC録画） | モードB（Claude が撮る） |
|---|---|---|
| 映り込み | 通知・タブ名・タスクバー・ブックマークが不意に入る | ページ内容だけ。**ブラウザのURLバーも入らない** |
| やり直し | 撮り直しは全部撮り直し | 1枚だけ撮り直せる |
| 同期 | 操作の瞬間に境界を合わせる作業が要る | **尺をナレーションから逆算**するのでズレない |
| 環境 | 制作者のPCに依存する | 誰の環境でも同じ画面になる |
| 待ち時間 | 実時間が動画に入る | 入らない（必要なら意図的に足す） |

一方、モードAにしかない良さもある：試行錯誤やエラーがそのまま教材になる。
**エラーの切り分けを見せたい回はモードA**、手順と画面の対応を見せたい回はモードB。

## 4つの収録モード（いずれも実証済み）

### B-1 クラウドIDE でコマンドを実行する回

エディタに該当のコードを開いたまま、**下のターミナルで1コマンドずつ実行する**固定レイアウト。
読んでいる行と実行結果が同じフレームに入るので「コードの読み解き」と噛み合う。

- 行送りはスクロールではなく**行番号ジャンプ**（スクロールは効かないことがある）
- ターミナルは**アカウント名がプロンプトに出ないシェル**を選ぶ
- レッスンのフォルダは事前にクリーンにする（前回の仮想環境や設定ファイルの残骸を消す）

#### 🔴 README の手順を「番号どおり・コマンドが見える形で」たどる（標準形）

実測（作り直し8本）で最も指摘が多かったのは「**動画を見ても、どのコマンドを打てばよいか分からない**」だった。
結果だけが映り、打ったコマンドが画面に出ていない区間があると、受講者は手元で再現できない。

- **教材側の README に、手順を番号つき・コピペできるコードブロックで書く**（venv 作成 → 依存 →
  設定ファイル → 実行 → 後片付けまで）。台本は「手順5で…」と README の番号で語る。
- 上半分に **README のプレビュー**（該当手順）、下半分に**ターミナル**を置き、
  **コマンドを打った状態（Enter 前）→ 結果** の2枚を1組で撮る。結果だけの区間を作らない。
- コードを読む区間だけエディターに切り替える。**撮影中はエディターの行間
  （`editor.lineHeight`）を 2.0 にする**と、強調枠を文字にかぶせずに置ける（撮り終えたら戻す）。
- シェルは README に合わせて固定する（例：Codespaces でも pwsh を選ぶ）。PowerShell なら
  **`Set-PSReadLineOption -PredictionSource None`** で予測候補の灰色の文字を消しておく
  （コマンドの後ろに履歴の断片が映り込む）。
- ⚠️ **キー入力の前に、フォーカスがターミナルにあるかを確かめる。** パネルが閉じていると
  エディターで開いているファイルに打ち込まれる（実測：データファイルを書き換えかけた。元に戻して `git checkout` した）。
- ⚠️ クラウドIDE（Codespaces）は**放置すると自動で停止する**。撮影の合間が空いたら、
  再開ボタンで起こしてからシェルの初期設定（PATH・予測候補の無効化）をやり直す。
- **出力が画面から流れ出ないように、教材の質問・プロンプトに答えの長さを指定する**（「2行で」など）。
  推論モデルは既定で長い Markdown を返し、ターミナルの1画面に収まらない（作り直し6本中4本で発生）。
- **デモが「通った」ことを画面で証明できる出力にする。** 例：ツール呼び出しの件数や、
  実際に実行されたコードの先頭を表示する。実測では、画面の数値は正しいのにツールは呼ばれておらず、
  モデルが暗算していた（旧版の「計算は Code Interpreter が担う」という説明に裏付けがなかった）。
- **撮影（save_to_disk）とスクロールを同じバッチに入れない。** 同じ時刻の画像が2枚できて取り違える。
- エディターの全角記号（＋・／など）が黄色の枠で囲まれるときは、`editor.unicodeHighlight.ambiguousCharacters`
  を撮影中だけオフにする（強調枠と紛らわしい）。行間と一緒に元へ戻す。
- `git pull` のあと README のプレビューが古いままのことがある。**プレビューを閉じて開き直す。**
- **1回の batch で保存するスクリーンショットは1枚まで。** 2枚保存すると、あとの処理が違う画像を拾うことがある。
- キー入力の直前に**ターミナルの中ほどを毎回クリック**する（下端近くではフォーカスが入らず、入力が消えた実測あり）。
  長い複数行のコマンドは1行ずつ入力する（続けて送ると連結して失敗した）。
- `git pull` のあと README のプレビューが古いままのときは、`Markdown: Refresh Preview`。
  それでも古ければ `Developer: Reload Window`（ターミナルの変数と venv は残る）。
- ターミナルに `4;68R` のような制御文字の断片が混ざったら、ターミナルごと作り直す。
- **Codespace の作業ツリーに他のレッスンの未コミットの変更があると、ステータスバーに `main*` が映り続ける。**
  撮影前に `git status` を見て片付ける。
- 実行結果に**サービスのアカウント名**（GitHub のユーザー名など）が出る回は、撮影計画の塗る対象に入れる。
- 撮影の担当を子エージェントに任せると、**1本で200ターン前後を使う**。操作は batch にまとめ、
  上限に近づいたら途中経過を書いてから止まるよう指示しておく（再開すれば続きから進む）。
- 撮影で README の誤り（コマンドが通らない・順序が逆）が見つかったら、**その場で README を直して
  push してから**撮り直す。画面の README と受講者の手元の README を一致させる。

### B-2 クラウドIDE でドキュメントを読み解く回

コマンドを実行しない回（設計・ワークシート・仕様の読み合わせ）。
**ターミナルパネルは閉じる**。空のターミナルが画面の1/3を占めても意味がない。

- Markdown は**プレビュー**で見せる。生のテキストだと表が読めない
- プレビューのフォントは既定のままだと動画で読めない。**20px 程度まで上げる**
- 準備のためにターミナルを使ったら、**撮る前にパネルごと閉じる**

### B-3 Web 管理コンソールをツアーする回

管理画面は**個人情報が出やすい**。塗りつぶしを前提に組み立てる（後述）。

- 画面遷移のあと **10〜15秒待つ**。管理コンソールは描画が遅い
- 右側のパネルが切れるときは**左ナビを折りたたむ**と収まる
- 1画面の情報量が多いので、**同じスクリーンショットに別の強調枠を描いて複数区間にする**

### B-4 CLI で作り、画面は「結果を読む」ために撮る回

クラウドの管理コンソールでウィザードを1画面ずつクリックしていく回は、**失敗率が高い**。
入力欄の位置が状態で動き、ドロップダウンは開いた直後に撮れず、確認ダイアログでタブが固まる。

**作る・壊すは CLI、画面は出来上がりを読むためだけに使う**、と割り切ると通る。
実測（クラウドのネットワーク機能7本）では、この形にしてから完走率が上がった。

- リソースの作成・変更・削除は CLI。**画面はクリックせず URL を直接組み立てて遷移**する。
- **CLI のエラー本文がそのまま教材になる。** 「この設定は保存できない」を口で言うより、
  返ってきたエラーコードと文面を端末画面として見せるほうが強い。
  仕様の裏取りにもなるので、**エラーは捨てずに控える**。
- 読み返しも CLI で行う。**⚠️ CLI で変更した直後の管理コンソールは、古い値を出し続ける**
  ことがある。ブレードを開き直しても反映されない。**画面を信じて説明を書くと間違える。**
- 端末画面（コマンドと出力を描いた静止画）と、コンソールのスクリーンショットを
  交互に並べると、「何をしたか」と「どう見えるか」が1本の流れになる。

## 🔴 収録前に決めること

1. **既定は「何も作らない・何も消さない」。** 課金リソースの作成、削除、送信ボタンは押さない。
   - **例外は、制作者が明示的に許可した回だけ。** その場合も条件は2つ：
     **撮り終えたら直ちに消す**ことと、**リソースグループが空になったことを確かめる**こと。
   - 許可のある回では、**教材側に「ここは課金が発生する。見るだけでもよい」と書く。**
   - ⚠️ **撮影の合間に長い待ちが入る回は、作りっぱなしで放置しやすい。**
     実測：待ちの間に作業が途切れ、課金リソースが5時間走り続けた。
     **作った時点で「いつ消すか」を決めておく。**
2. **サインインは代行しない。** 資格情報の入力が要る画面に来たら止めて、制作者に頼む。
3. **表示言語を決める。** 受講者の環境に寄せるか、資料の表記に寄せるか。画面と資料が
   食い違うと必ず指摘される。日本語UIで撮るなら、資料とナレーションで英語名を併記する。
4. **塗る対象を先に列挙する。** 撮ってから考えると漏れる。
5. **待ち時間を先に見積もる。** 下記。
6. **共有リソースを「壊す」回は、練習用のリソースグループで撮る。** 講座全体で使い回す
   リソース（共通のリソースグループ・AI リソース）に対して、認証方式の無効化・設定の書き換え・
   削除を行うと、**後続のレッスンが動かなくなる。** その回だけは
   **練習用の RG を作る → 撮る → RG を削除 → 論理削除されたリソースを purge** までを手順に含める。
   - 教材の README にも、この「作成 → 削除 → purge」を番号つきの手順として書く（受講者も同じ道をたどる）。
   - **purge まで撮る。** 論理削除（soft delete）が残るサービスは、名前やクォータを
     しばらく（例：48時間）つかんだままになる。`list-deleted` で出る → purge → もう一度
     `list-deleted` で空、までを見せる。
   - 削除の前に、**変数が練習用の RG を指していることを画面で確かめる**区間を1つ入れる。
   - 読むだけ・呼ぶだけの回は、共有リソースをそのまま使う（受講者が毎回作り直さずに済む）。
   - **リージョンは作る前にクォータで選ぶ。** 実測：East US 2 は動画生成モデルの枠を講座外のリソースが使い切っていて
     デプロイが `InsufficientQuota` で失敗し、Sweden Central に作り直した。`az cognitiveservices usage list` で先に確かめる。
   - **続けて撮る2本が同じ高価なリソースを使うなら、1つの RG にまとめて後の回で消す**（例：検索サービスを
     2本で共有し、後の回の最後で削除）。引き継ぎ（名前・SKU・残したロール）を撮影担当に渡す。
   - **RG の外に付けたロール**（例：検索サービスの MI から共通の AI リソースへの割り当て）は、RG を消しても残る。
     **RG を消す前に外す**手順を README に入れる。

## ⚠️ プロビジョニングの待ち時間を、撮影計画に先に書く

動画には待ち時間が入らないので軽く見積もりがちだが、**撮影の所要時間はほぼ待ちで決まる**。

実測（クラウドのネットワーク機能）：

| 対象 | 作成〜利用可能 |
|---|---|
| VPN のゲートウェイ | 約 20 分 |
| 専用線のゲートウェイ | 約 25 分 |
| レイヤー7 のロードバランサー | 約 8 分 35 秒 |
| CDN/エッジのルート追加 → 実際に配信され始めるまで | 約 19 分 36 秒 |
| CDN/エッジのキャッシュ設定 → 実際に効き始めるまで | 約 10 分 40 秒 |

したがって：

- **撮影計画に「作る → 待つ → 撮る → 消す」の時刻を書く。** 待ちの間に別の準備を進める。
- 🔴 **設定を1つ変えるたびに10〜20分待つサービスは、実機演習に向かない。**
  1本の中で複数の設定を試す構成だと、待ちが積み上がって収録が終わらない。
  **そういう回は最初から画面ツアーに倒す**（作成 → 確認 → 削除だけを撮り、
  挙動の違いはスライドで説明する）。着手前に判断すること。
- 待ちは**分割したポーリング**で回す（1回の待機には上限がある）。
  待ちを回している間も、**課金は動いている**。

## 🔴 塗りつぶし（公開前の必須工程）

**ぼかしは使わない。** 条件次第で復元されうるし、「隠したつもり」が残る。
`redact.py` で**黒ベタ**にする。不可逆で、視聴者にも「伏せてある」と伝わる。

典型的な対象：

| 対象 | よく出る場所 |
|---|---|
| 氏名・表示名 | ダッシュボードの挨拶、アカウントメニュー |
| メールアドレス | 作成者・更新者の列、メンバー一覧 |
| テナント/サブスクリプション/リソースの ID | 詳細パネル、URL を含むフィールド |
| **他プロジェクト・他リソースの名前** | 横断の一覧、切替ドロップダウン |
| コストの実額 | 概況ダッシュボード |

補足：

- **切替ドロップダウンは開かない。** 他の作業物の名前が一覧で出る。
  スコープを変えたいときは**URL を直接組み立てて遷移**する。
- ブラウザ拡張が PII を自動でぼかすことがあるが、**それに頼らない**。必ず上から黒ベタで潰す。
- 座標は `redact.py --probe` で**先に拡大して確かめる**。当てずっぽうで塗ると端から文字がはみ出す。
  - 実測：表形式の出力（scope 列の ID など）は、**折り返しや桁のずれで行ごとに右端が違う**。
    1行分の幅で塗ると、別の行で末尾の数文字が残った（2本で発生）。**全行を原寸で見て、最も長い行に合わせる。**
- 塗ったあと、**全フレームを目視する**。1枚ずつ見る以外に確かめる方法はない。
- 教材として必要な値（受講者が次のレッスンで実際に使うエンドポイントなど）は**塗らない**。
  「リソース名を塗る」は他人の作業物を指す。

## ブラウザ操作の実測ルール

ここは何度も踏み直した落とし穴なので、そのまま従うこと。

### 保存とサイズ

1. 🔴 **保存の指定を忘れると、撮ったはずの画像がどこにも残らない。** スクリーンショットは
   既定では返ってくるだけで、ディスクには書かれない。**保存のオプションを明示する**。
   実測：この取りこぼしで1レクチャー分（8枚）を丸ごと撮り直した。**撮ったあとは
   必ずファイルの存在と寸法を確かめてから次の操作に進む。**
2. 🔴 **保存と縮小指定を同時に使わない。** 縮小指定は**保存ファイルにも効く**
   （実測：1512x792 で撮ったつもりが 937x491 で保存された）。
   確認用に小さく見るのと、素材として保存するのは**別の呼び出し**にする。
3. **撮影サイズは1本を通して固定する。** 揃わなかった分は組み立て側で吸収できるように
   しておくとよい（`build_rec.py` に渡す前に、全フレームを1つのキャンバス寸法へ揃える）。
   が、**揃える前提で撮るほうが画質が落ちない**。

### 🔴 画面が少しずつ小さくなる（解像度の劣化）

**症状**：撮るたびに1枚の情報量が減っていく。実測では CSS ピクセル幅が
**1792 → 1254 → 778** と段階的に縮んだ。

**原因**：操作のタイムアウトが、ブラウザ側に**表示倍率の上書きを残す**。これが
**呼び出しのたびに積み上がる**。ページの再読み込みでも、ウィンドウのリサイズでも、
OS レベルの倍率リセット（Ctrl+0）でも**戻らない**。

**唯一効いた対処：タブを閉じて新しいタブを作る。** 認証のやり直しが要るので安くはない。

したがって：

- **1タブで長く撮らない。** 「良いフレームを撮る → 次へ」を小刻みに回し、
  縮み始めたら**惜しまず撮り直す前にタブを作り直す**。
- **縮みは目視では気づきにくい。** 保存のたびに寸法を確かめる（上の1.と同じ習慣で拾える）。
- タイムアウトを出さないことが最良の予防になる。長い待ちは分割する（下記）。

### クリックと入力

4. **座標クリックは当てにしない。** ビューポートが呼び出しごとに変わる（実測で
   1374x730 / 1425x712 / 1512x803 / 1568x783 が混在した）。**要素を名前で探して
   ref を取ってからクリックする**。1つ前のスクリーンショットの座標は、もう合っていない。
5. ⚠️ **ただし ref クリックも万能ではない。** 仮想スクロールや独自描画を多用する
   管理コンソールでは、**ref を取れてもクリックが素通りする**ことがある。実測（クラウドの
   ネットワーク管理画面）では、ウィザードの入力欄とドロップダウンで繰り返し失敗した。
   - まず **ツール側が報告してきた座標系**で押す（自分で換算し直さない）。
   - **レイアウトが変わったら必ず読み直す。** 折りたたみ・タブ切替・パネルの開閉のあとの
     ref と座標は、もう別物である。
   - **2〜3回失敗したら操作をあきらめて B-4（CLI 先行）に切り替える。**
     同じクリックを粘るのが、この作業で最も時間を溶かすパターンだった。
6. **ターミナルは1文字目が落ちる。** コマンドの先頭に半角スペースを1つ入れる。
7. **打ち直しは Esc ではなく Ctrl+C。** Esc では入力行が消えず、途中に挿入される。
8. **ツールバーのボタンを押した直後はツールチップが残る。** 別の場所にポインタを移して
   3秒待ってから撮る。
9. **通知・コーチマークは本文ではなく閉じるボタンを押す。** 本文を押すと別の画面に飛ぶ。
10. **ダイアログを出さない。** モーダルが出ると以後の操作を受け付けなくなる。
11. 長い待ちは分割する。1回の待機に上限があるので、10秒×N回に分ける。

### ⚠️ Git Bash から CLI を叩くときのパス変換

Git Bash（MSYS）は、**`/` で始まる引数を Windows のパスへ勝手に書き換える**。
`--path /` が `--path 'C:/Program Files/Git/'` になって渡る。

実測での被害：ロードバランサーの正常性プローブのパスが化け、プローブが恒久的に
異常のままになった。**コマンドは成功扱いで返る**ので、20分デバッグして
やっと気づいた。同じ事故は `--ids` でも起きる。

```bash
MSYS_NO_PATHCONV=1 az network lb probe update ... --path "/"
```

**`/` で始まる値・リソースIDを渡すときは必ず `MSYS_NO_PATHCONV=1` を付ける。**
付け忘れは、エラーではなく**間違った設定**として残るので、
**CLI で設定したら CLI で読み返して値を確かめる。**

## フレームの組み立て

`build_rec.py` に任せる。要点は3つ。

### 🔴 尺は「合成した音声の実尺」から決める。文字数の見積もりを流用しない

`尺 = 文字数 / cps × 1.15 + 余白` は、**音声がまだ無い段階の当て推量**である。
これをそのまま完成尺にすると、**見積もりの余裕がそのまま無音になる**。

実測：文字数見積もりで組んだ回は沈黙率が2割を超え、区間によっては
ナレーションが終わってから4秒以上静止画を眺めることになった。

**正しい順序は2パスである。**

```
1パス目  台本 → TTS（音声だけ先に合成する）
2パス目  各 wav の実尺を測る → 尺 = 実尺 + 末尾余白 → フレームを組む
```

- `build_rec.py --audio-dir <音声ディレクトリ>`（または `--durations <json>`）を渡すと、
  文字数見積もりではなく**実尺**で尺を決める。**渡さなければ従来どおり見積もりに落ちる**ので、
  音声が用意できる回では必ず渡す。
- **末尾余白（`--tail-sec`）は 2.0 秒。** 実測7本での結果は
  **沈黙率およそ10%・最大の無音 3.7〜4.1秒・本ごとのばらつき 0.1秒**。
  狙った帯（10〜20%）の下端にきれいに収まり、本ごとのブレもほぼ無い。
- 見積もりパスに残っている `--cps` / `--headroom` / `--pad-sec` は、
  **音声をまだ作れない下見のときだけ**使う。

### スクリーンショットは拡大縮小しない

ビューポートが揺れるので、スケールし直すと区間ごとに文字の大きさが変わって見える。
**キャンバスへパディングするだけ**にする。キャンバスより大きい図版だけ、収まるように縮める。

図解の回は `stage_diagram.py` で段階図を作る。**全段に不可視の白枠を入れて
外接矩形を固定する**のを忘れないこと（入れないと段ごとに図が伸縮する）。

### ⚠️ 端末フレーム（コマンドと出力を描いた静止画）は ASCII だけで書く

B-4 で多用する。等幅フォントは**日本語グリフを持たないことがあり、`?????` になる**
（実測：Consolas で全滅し、テキストとタイトルを全部書き直した）。

- **本文もタイトルも ASCII のみ。** 説明したいことはナレーションで言う。
- 描画は**固定の行ピッチ**で積む。強調したい行の矩形は**数えずに式で出す**：

  ```
  y = 先頭行のベースライン + 行ピッチ × (行番号 - 1)
  ```

  実測の値（1行目 y=52 / ピッチ 26px）なら、`n` 行目の強調矩形は
  `(x0, 52 + 26*(n-1) - 5, x1, 52 + 26*(n-1) + 24)`。
  **矩形を目分量で置くと必ず半行ずれる。**
- **1画面に入る行数と桁数を先に決めて、テキストをそこへ収める。**
  実測のキャンバス（1512x792・上下余白80px）で **(792-80)/26 = 27行・118桁**。
  あふれた行は黙って切れるので、**長い出力は抜粋して載せる**。
- 端末フレームは「何をしたか」、コンソールのスクリーンショットは「どう見えるか」。
  **交互に並べる**と1本の流れになる。

### 強調（クリック位置・注目箇所）の付け方

実測で固まった作法。

- **種類は3つに絞る。** `look`（読ませる）/ `click`（押す）/ `type`（入れる）。
  増やしても視聴者は区別しない。
- **一度に1つだけ出す。** 同じフレームに2つ以上の強調枠を出すと、どちらを見ればよいか
  分からなくなる。見せたい箇所が複数あるなら**同じ画像で区間を分ける**。
- **切り替えは 0.3 秒のクロスフェード。** 瞬間的に切り替えると点滅して見える。
- **周囲の減光は 0.45 程度。** これ以上暗くすると周辺の文脈が読めなくなり、
  これ以下だと強調が効かない。
- **横に長いフィールドは、枠の左端に寄せて丸を置く。** 中央に置くと
  「どこを押したのか」が伝わらない。
- **ラベルはフレームの内側に収める。** 画面の端を指す強調では、ラベルが外へ出て切れる。
- 🔴 **強調の位置は、レンダリングした静止画を見るまで信用しない。**
  座標の写し間違いは数値を見ても分からない。検収の手順は次節。

### 🔴 組み立てる前に、強調を1枚ずつ目で確かめる

実測：4レクチャーで**矩形の誤り9件**が見つかった。うち**数値レビューで気づけたものは0件**。
すべて「描いた絵を見て」初めて分かった。

```bash
# レシピ（redact.py と同じ JSON）から、強調を当てた絵とコンタクトシートを作る
python scripts/cue_stills.py recipe.json --src-dir ./raw --out-dir <作業ディレクトリ>/stills --sheets --stills

# すでに加工済みのフレームがあるとき
python scripts/cue_stills.py --frame-dir <作業ディレクトリ>/frames --out-dir <作業ディレクトリ>/stills --sheets
```

- **抜き取りでは当たらない。** 誤りは1本あたり1〜6件で、30〜50枚の中に散らばる。
- **コンタクトシート（4枚/枚）で見る。** 1枚ずつ読むのに比べて画像のコストが約1/4になり、
  それでも矩形のずれは十分に見える。
- この検収は**動画を組む前**に済ませる。組んだあとに直すと、音声の合成からやり直しになる。

## 🔴 「効くまでの時間」を計るスクリプトの作り方（3回やり直した）

反映に時間がかかるサービス（CDN/エッジ、ゲートウェイ、DNS の伝播など）で
「変更 → 効くまで」を計るとき、**計測そのものを間違えやすい。** 実測では、
**同じレクチャーの観測を3回撮り直し、数時間を失った。** 原因は全部、スクリプトの作りだった。

### 1. 「実物が返った」を待つ。既定のエラーページを「有効」と数えない

待ち条件を「200 か 404 が返る」にしたら、**サービスが返す既定の 404 ページ**（ルートがまだ無い状態の応答）を
「有効になった」と誤判定した。**中身（自分で置いたファイルの文字列）が返ったことを条件にする。**

さらに、**新しく作ったものが行き渡るまでの待ちが、その後の変更の待ちに混ざる。**
新しいルートは、作成コマンドが返ってから**最初の実応答まで 20分33秒**（別の回では 19分36秒）かかった。
その待ちの最中に「キャッシュを有効にする」「規則を結びつける」を投入したら、
**「約18分」「約13分」という、変更の反映時間ではない数字**が出た（実際は新しいルートが行き渡る時間）。

→ **土台が「実物を返す」ことを確かめてから、変更を1つずつ、直列に投げて計る。**

実測（有効になったルートに対して、1つずつ）：

| 変更 | 効くまで |
|---|---|
| 新しいルートを作る → 最初の実応答 | **約 20 分** |
| キャッシュを有効にする → `X-Cache` が変わる | 724 秒（約 12 分） |
| 規則セットを結びつける → 302 が返る | 154 秒（約 2.5 分） |
| 配信元ホストヘッダーを壊す → エラーが返る | 210 秒（約 3.5 分） |
| 配信元ホストヘッダーを戻す → 復帰 | 735 秒（約 12 分） |
| 配信元を無効にする → 別の配信元が応答 | 575 秒（約 9.5 分） |
| 配信元を有効に戻す → 元の配信元が応答 | 754 秒（約 12.5 分） |

**変更ごとに幅が大きい。** 「最大15分」のような公称値を、そのまま実測として書かない。

### 2. 判定を `$(...)`（サブシェル）の中で回さない

判定のたびに「まだ叩いていないパス」の通し番号を進めていたが、**関数を `$(...)` で呼ぶと、
カウンターの更新が親に戻らない。** その結果、**すでにキャッシュに入ったパスで「復帰した」と誤判定**
（「1秒で復帰」）し、証拠に載せたパスも、本当はキャッシュ済みだった。

→ 判定は**親シェルの中で**回す。カウンターは**ファイルに持つ**と、途中で止めても続きから使える。
→ 判定に使うパスは、**毎回まだ一度も要求していないパス**にする（キャッシュのキーはパスごと）。
   使い切ったら止まるようにしておく（残りが無いのに続けると、判定が壊れる）。

### 3. 一時的な失敗を「壊れた」と数えない

1回の失敗（タイムアウトなど）を「壊れた」と数えると、実際には何も起きていないのに
「壊れた」と記録される。**連続2回そろって初めて数え、時刻は最初の1回のもの**にする。

### 4. 失敗を検知したら、待たない

- **変更コマンドが失敗したのに、そのまま「効くまで待つ」ループに入った**ため、上限の40分を空費した
  （変更していないので、永遠に効かない）。**変更コマンドの終了コードを見て、失敗なら即座に止める。**
- **前提が満たされていないのに、成功を待つループを30回まわして42分失った**
  （前段の作成が失敗して IP が空だった。空の値に対する判定は、毎回「届かない」になる）。
  **ループに入る前に、前提（変数が空でないか、リソースがあるか）を確かめる。**
- ループの上限は**回数**でも**時間**でも必ず持つ。1回が1分かかる操作（VM への実行コマンドなど）は、
  回数を少なくする（6回まで、など）。

### 5. 止めるときは PID で殺す。後片付けは別スクリプトにする

Windows では、`TaskStop` で「止めた」つもりでも、`bash` 本体は生き残る。
実測では、**生き残りが同じ配信元を同時に触って計測が混ざり、最後にリソース グループまで削除してしまった。**

- 止めたら、`Get-CimInstance Win32_Process | ? CommandLine -match '<スクリプト名>'` で残りを確かめ、
  `Stop-Process -Id <PID> -Force` で殺す。
- **クラウドの状態を変えるスクリプトには、先頭に排他ロック**（`mkdir <lockdir>` と `trap 'rmdir' EXIT`）。
- **末尾に `az group delete` を持つスクリプトは、止めたいときほど危ない。**
  観測が終わっていない段階で走り切らないよう、**後片付けは別スクリプト**に分ける。

### 6. 「壊す」観測は、最後の1つを壊せるかを先に確かめる

「配信元を無効にする」観測は、**ルートに結びついたオリジン グループの最後の1つを無効にすると、
BadRequest で拒否された**（`Cannot disable or delete the last origin ...`）。
**2つ目を足して、片方を無効にする**形に組み直した（優先度2のスタンバイを置き、
無効にすると応答がスタンバイへ移る、という、より実務に近い見せ方になった）。
**壊す観測は、撮る前に「本当にその操作が通るか」を1回試す。**

## 🔴 Windows の Git Bash で踏んだ罠（追加）

- **`az ... -o tsv` の出力には CR（`\r`）が付く。** `for b in $(az ... -o tsv)` や
  `NAME=$(az ... -o tsv)` の値をそのまま次のコマンドへ渡すと、**リストの先頭の要素だけ**
  `InvalidUri` などで落ちることがあった（末尾の要素は通るので、気づきにくい）。
  **値を取るときは `| tr -d '\r'`**。
- **Bash ツールのヒアドキュメントに、バックスラッシュや引用符が多い Python／シェルを埋めない。**
  `\\` が半分になる・終端が認識されないなどで、置換が黙って 0 件になった。
  **バックスラッシュを含むスクリプトは、Write ツールでファイルに書いてから実行する。**
- **Windows の Python に渡すパスは `cygpath -w` で変換する。** `/c/Users/...` のまま渡すと
  `can't open file 'C:\\c\\Users\\...'` になる。ポーリングの中でこれをやると、**30 分の上限まで毎回失敗して気づかない**。
  ポーリングの最初の 1 回は、**判定結果をそのまま画面に出して**確かめる。
- **`--no-wait` の作成は、エラーを返さない。** 拡張機能（azure-firewall など）が
  「本体を作る → IP 構成を足す」を分けて行うコマンドでは、`--no-wait` だと後半が走らず、
  **「作れてしまった」ように見える**（負の検証が成立しない）。**負の検証は同期で、`timeout` を付けて**行う。
- **独立した実習は、別のリソース グループで並列に走らせてよい。** 3 本を同時に走らせて問題なかった
  （待ち時間が長い実習ほど効く）。**ロック用ディレクトリとログは実習ごとに分ける。**

## 収録は「資料の事実確認」として最も収穫が大きい

実測：12本を撮って、**12本すべてで解説ドキュメントに直しが入った**。
手元で動かして初めて分かることが、机上のレビューでは残っていた。

拾えたものの例：

- CLI のオプションが**存在しない／別名になっている**
- ある設定の組み合わせが**そもそも保存できない**（返ってくるエラーコードが根拠になる）
- 画面のラベルや階層が資料の記述と違う
- 「この値はここで確認できる」と書いた場所に、実際には出ていない
- **「消すと残る」「消すと消える」のような、削除の挙動の主張。** 資料に無い推測が解説の**核心**になっていて、
  実際に消してみると逆だった（フローログの設定は、対象の VNet と一緒に消えた）。
  **推測を核心に据えた解説ほど、撮る前に「1つずつ消して確かめる」実験を組む。**
- **ログやレコードの見た目（パス・桁数・単位・名前の接頭辞）。** 資料に例が無いところは、
  解説が別の種類のログの形を流用していて、実物とは違った（blob のパス、時刻がミリ秒、規則名に `UserRule_` が付く）。

だから：

- **撮りながら気づいたことは、その場で解説ドキュメントへ書き戻す。**
  あとでまとめて直そうとすると、何が実測で何が記憶か分からなくなる。
- **最終確認日を更新する。** 実機で見た日付が、その記述の根拠日になる。
- **できなかったことは「できない」と書く。** 代わりの手段を2〜3通り添える。
  エラーの回避策こそ受講者が最も必要とする情報である。

## git に入れるもの・入れないもの

| 対象 | 扱い |
|---|---|
| 解説ドキュメント（実測を反映したもの） | **コミットする** |
| `<basename>_transcript_rec.md`（録画パートの台本） | **コミットする** |
| `<basename>_rec.mp4`（素材の録画） | git 管理外 |
| `<basename>.mp4`（完成動画） | git 管理外 |
| `<basename>_audio_rec/`（音声と manifest） | git 管理外 |
| `<basename>_rec.work/`（作業用） | git 管理外 |

- **`git add -A` を使わない。** 作業ディレクトリに巨大な中間生成物が落ちているので、
  パスを明示して `git commit -- <path>...` の形で入れる。
- コミット単位は**レクチャー1本**。メッセージに「実機に合わせて資料を直した」ことを書く。

## ⚠️ 既存の録画を上書きしない

`<basename>_rec.mp4` は、制作者が撮った元録画と同じ名前である。多くの構成で
この拡張子は git 管理外なので、**上書きすると復元できない**。
`build_rec.py` は既存ファイルを `.previous.mp4` に退避してから書き出す。
